## 二、用户认证接口测试

### 2.1 发送验证码

#### 接口信息
- **接口**: `POST /api/auth/send-code`
- **描述**: 发送短信验证码
- **认证**: 无需认证

#### 测试用例 AUTH-API-001: 正常发送验证码

**请求参数:**
```json
{
  "phone": "13800138000",
  "type": "login"
}
```

**预期响应 (200):**
```json
{
  "code": 200,
  "message": "验证码已发送",
  "data": {
    "phone": "13800138000",
    "expireIn": 300,
    "cooldown": 60
  }
}
```

**验证点:**
- ✓ HTTP状态码为200
- ✓ 数据库中创建验证码记录
- ✓ 验证码有效期为5分钟
- ✓ 短信发送成功（检查日志）
- ✓ 返回冷却时间60秒
> 说明：`phone/expireIn/cooldown` 为后端当前实现返回的扩展字段，属于语义等价类-B（返回体扩展字段）；前端最小合同只需依赖“请求是否成功 + 是否进入冷却期”，字段命名以实现为准。

#### 测试用例 AUTH-API-002: 手机号格式错误

**请求参数:**
```json
{
  "phone": "138001380",
  "type": "login"
}
```

**预期响应 (400):**
```json
{
  "code": 400,
  "message": "手机号格式错误",
  "error": "INVALID_PHONE_FORMAT"
}
```

**验证点:**
- ✓ HTTP状态码为400
- ✓ 不发送短信
- ✓ 不创建验证码记录

#### 测试用例 AUTH-API-003: 验证码发送频率限制

### 2.2 用户注册

#### 接口信息
- **接口**: `POST /api/auth/register`
- **描述**: 用户注册
- **认证**: 无需认证

```json
{
  "phone": "13600136000",

  "grade": "初三",
  "age": 15,
  "school": "星河中学"
}
```

**预期响应 (201):**
```json
{
  "code": 201,
  "message": "注册成功",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refreshToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",

      "grade": "初三",
      "age": 15,
      "school": "星河中学"
    }
  }
}
```

**验证点:**
- ✓ HTTP状态码为201
- ✓ 数据库创建用户记录
- ✓ 从白名单分配角色
- ✓ 白名单标记为已注册
- ✓ 返回JWT token
- ✓ 学生包含年级、年龄与学校字段
> 说明：返回体结构与 `auth.service.register` 的实现保持一致，采用 `data.token/data.refreshToken/data.user.*` 形式；与部分早期文档中直接在 `data` 下平铺 `userId/token/refreshToken` 的写法属于语义等价类-A/B（命名与结构增强），以实现与本测试文档为准。

### 15.1 登录 / 注册全链路（E2E-API-001）

**目标:**
- 验证从前端输入手机号开始，到收到验证码、完成注册/登录、进入首页的完整用户路径。

**前置条件:**
- 后端服务已启动且数据库迁移完成；
- 前端应用已在浏览器可访问（例如 `http://localhost:5173`）；
- 测试手机号已在白名单（注册场景），或对应用户已存在（登录场景）。

**步骤（学生注册 + 登录示例）:**
1. 打开登录/注册页面；
2. 在手机号输入框中输入合法手机号（例如 `13900002001`）；
3. 点击「获取验证码」，观察前端调用 `POST /api/auth/send-code` 成功，按钮进入倒计时；
4. 在验证码输入框中填入 `123456`；
5. 填写昵称、年级、学校等必填信息；
6. 点击「注册并登录」按钮；
7. 完成后自动跳转到主列表页，页面头部或个人信息区域显示正确昵称和角色。

**预期结果:**
- ✓ 前端无报错弹窗/console error；
- ✓ 对应的 `send-code` / `register` / `login` 接口返回符合「二、用户认证接口测试」中约定的响应结构；
- ✓ 浏览器本地存储（例如 localStorage）中存在 JWT 或等价登录状态，并在后续请求中自动携带；
- ✓ 刷新页面后仍保持登录态（前端使用 token 重新获取 `/api/auth/me` 或等价接口）。

### 15.3 提问 → 审核 → 展示（E2E-API-003）

**目标:**
- 验证从学生/教师前端发起提问，到教师审核通过，再到问题出现在前端列表/详情页的完整链路。

**前置条件:**
- 至少一名学生账号和一名教师账号；
- 学生课时有效（未过期）。

**步骤:**
1. 以学生身份登录前端；
2. 进入「提问」页面，填写标题（≤100 字）与内容，提交后前端调用 `POST /api/questions`；
3. 验证提交成功后，前端给出「待审核」提示，且在当前用户「我的提问」页中显示状态为 pending；
4. 以教师身份登录前端管理/审核页面，调用 `GET /api/admin/audit/pending?type=question` 获取待审核列表；
5. 在审核页面对该问题执行「审核通过」，触发 `POST /api/admin/audit/:contentId/approve`；
6. 返回学生端列表页，刷新或重新进入；
7. 在普通列表页中找到该问题，点击进入详情页。

**预期结果:**
- ✓ 学生提问接口返回 HTTP 201，问题在数据库中 `status=pending`；
- ✓ 教师审核通过后，问题 `status=approved`，`isGoodQuestion`、`score` 等字段按审核输入更新；
- ✓ 前端列表页仅在状态变为 approved 后才显示该问题；
- ✓ 详情页内容与问题字段（标题/内容/标签/难度等）一致。
