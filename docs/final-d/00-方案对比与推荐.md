# 方案对比与推荐（本地 + 云服务器兼容版）

## 场景目标
- 前端：Vite 构建产物（你当前路径是 `/mnt/c/Users/Administrator/Downloads/zsxq-4/dist`）
- 后端：Express，端口 `3000`
- 数据层：PostgreSQL（Prisma）+ Redis
- 网关：Caddy（自动 HTTPS）
- 要求：同一套配置可在本地和云服务器复用

## 方案对比

### 方案 A（推荐）：单套 Compose + 参数化变量（域名/路径/镜像）
- 优点：本地和云端共用一份 `docker-compose.yml`
- 优点：通过 `.env.deploy` 切换环境，不改 YAML 主体
- 风险：需要严格维护 `.env.deploy`，防止变量填错
- 适用：你当前“能跑 + 易改”的目标

### 方案 B：本地与云端维护两份 Compose
- 优点：每份文件直观、独立
- 风险：长期容易漂移（本地修了，云端忘记同步）
- 适用：环境差异非常大时

### 方案 C：前端也容器化（Nginx），不挂载 dist
- 优点：交付形态更封装
- 风险：构建链路更长，调试成本更高
- 适用：团队化和标准化发布阶段

## 推荐方案
- 推荐采用 `方案 A`
- 关键做法：
- 用 `.env.deploy` 控制 `SITE_ADDRESS`（域名/本地地址）
- 用 `.env.deploy` 控制 `FRONTEND_DIST_PATH`（本地/云路径）
- 用同一份 Caddy 规则完成 `/api` 反代与前端静态托管
