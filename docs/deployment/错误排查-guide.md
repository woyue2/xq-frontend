# 系统日志与错误码判断方法论（本地联调与测试场景）

> 目标：为团队成员提供一套统一的方法，用于在本地或测试环境下判断「接口返回码 + 系统日志」是否符合项目规范，从而更稳定地定位问题、评估质量。

---

## 一、判断逻辑的具体步骤

### 1. 明确本次"行动"的边界

1. 确定当前要验证的"行动"类型：
   - 登录 / 发送验证码 / 刷新 Token 等认证行为；
   - 提问、回答、评论、点赞、收藏等业务行为；
   - 审核、课时管理、白名单管理等管理行为；
   - 内部诊断 / AI 回调 / 埋点上报等内部行为。
2. 明确期望结果：
   - 本次请求预期是「成功」还是「失败」？
   - 成功时应该返回什么 HTTP 状态码和业务 `code`？
   - 失败时应返回什么错误码和错误文案？

### 2. 触发行为并收集三类信息

1. 在前端页面或接口调试工具（Postman、Thunder Client 等）中发起请求；
2. 同时在后端控制台或日志系统中观察对应日志（Pino 输出）；
3. 至少收集以下三类信息：
   - **请求信息**：method、url、请求体关键字段（脱敏后理解即可）；
   - **响应信息**：HTTP 状态码、响应体中的 `code`、`error`、`message`；
   - **系统日志信息**：
     - 访问日志：`req.method`、`req.url`、`res.statusCode`、`responseTime`；
     - 错误日志（如有）：`type`、`status`、`code`、`error`、`path`、`method` 等。

### 3. 建立"请求 → 响应 → 日志"的对应关系

1. 根据时间戳、`req.id`（pino-http 自动维护的请求 ID，如有）与 `method + url` 确认同一请求；
2. 确认以下对应关系是否成立：
   - HTTP 状态码 == 响应体中的 `code`；
   - 访问日志中的 `res.statusCode` == HTTP 状态码；
   - 错误场景下，错误日志中的 `status` 与 `code` == HTTP 状态码；
   - 错误场景下，错误日志中的 `error` 与 响应体中的 `error` 相同。

### 4. 对照规范进行判断

1. 成功场景：
   - 状态码 / `code` 是否为 2xx（通常为 200 或 201）；
   - 响应体是否包含预期数据结构（字段名、类型、必填项）；
   - 访问日志中的 `res.statusCode` 是否为 2xx；
   - 不应该出现错误日志（`type` 不应为 `app_error` / `validation_error` / `unknown_error`）。
2. 失败场景：
   - 状态码 / `code` 是否为 4xx 或 5xx；
   - 错误码 `error` 是否符合约定（如 `UNAUTHORIZED`、`VALIDATION_ERROR`、`INTERNAL_SERVER_ERROR` 等）；
   - 错误日志是否存在，且结构化字段（`type/status/code/error/path/method`）是否完整；
   - 文案是否清晰、不暴露敏感信息。

### 5. 对异常情况进行分类

当发现"不一致"时，将问题归类：

1. **契约不一致**：响应结构或字段值与后端测试用例 / 文档约定不一致；
2. **日志不完整**：访问日志或错误日志缺少关键字段，或无法通过日志定位请求；
3. **状态码不合理**：明明是业务异常却返回 200 / 500，未区分 4xx / 5xx；
4. **文案不合规**：错误消息不清晰、中文表述不规范、暴露内部实现细节；
5. **安全问题**：日志中包含敏感信息（如完整手机号、验证码、Token 等）。

## 二、适用场景说明

本判断方法论适用于以下典型场景：

1. **本地前后端联调**：
   - 开发者同时启动前端（Vite）与后端（Express + Prisma），在浏览器上操作业务流程；
   - 通过控制台日志快速验证接口是否按规范返回正确码/错误码，且日志可用于问题追踪。
2. **集成测试回归**：
   - 在后端执行 Jest 集成测试（如 `auth.api.spec.ts`、`behavior.api.spec.ts` 等）时；
   - 结合测试输出与 Pino 日志，判断接口行为是否与文档和测试用例一致。
3. **问题排查与复现**：
   - 测试或运营同学反馈线上/测试环境问题后，开发者在本地复现；
   - 利用系统日志中的 `status/code/error/path/method` 快速定位异常请求和原因。
4. **质量审计 / Code Review**：
   - 审查新接口或改动时，验证是否遵守统一的错误处理与日志规范；
   - 通过阅读中间件代码与示例日志，对照本方法论给出改进建议。

## 三、质量评估标准

### 1. 正确性维度

1. 状态码与错误码一致性：
   - HTTP 状态码与响应体中的 `code` 一致；
   - 日志中的 `status` 与 `code` 与响应保持一致；
   - 错误场景下，`error` 字段与文档约定保持一致。
2. 契约稳定性：
   - 响应结构满足文档定义，兼容已有测试用例；
   - 不随意改变成功 / 失败的状态码语义（例如不把业务异常统一改成 200）。

### 2. 可观测性维度

1. 访问日志是否完整：
   - 请求到达时有访问日志；
   - 完成时有包含 `statusCode` 与 `responseTime` 的日志记录；
   - requestId（如 `req.id`）可在日志中被识别，便于串联。
2. 错误日志是否结构化：
   - 必备字段：`type/status/code/error/path/method`；
   - 可选字段：`stack`（在开发/测试环境）、`userId`（如安全可控）、额外上下文信息。

### 3. 安全性与合规性维度

1. 日志中不包含以下信息的明文：
   - 短信验证码、Token、密码、身份证号等；
   - 完整手机号等敏感信息（必要时需脱敏）。
2. 错误消息不泄露内部实现细节：
   - 500 错误不返回具体堆栈或 SQL 文本；
   - 使用通用文案（如"服务器内部错误"）对外，只在日志中保留详细堆栈。

### 4. 可测试性维度

1. 单元测试覆盖关键中间件逻辑（如 `error.middleware.ts`、`logger.middleware.ts`）：
   - 覆盖 `AppError`、`ZodError`、未知错误三类分支；
   - 覆盖 `req.log` 存在与缺失两种路径；
   - 对响应结构与日志调用参数进行断言。
2. 覆盖率指标：
   - 中间件文件的行覆盖率、分支覆盖率不低于 85%；
   - 整体后端测试行覆盖率接近或高于 80%。

## 四、常见问题的判断依据

### 问题 1：接口明明失败，但 HTTP 状态码是 200

**判断依据：**

1. 响应体中 `code` 是否非 200，但 HTTP 状态码仍为 200；
2. 错误日志中是否记录了 `type='app_error'` 或 `type='validation_error'`；
3. 业务代码是否通过"返回错误码而不是抛出异常"来表示失败。

**处理建议：**

1. 对于真正的业务错误，应抛出 `AppError`，由错误中间件统一转换为 4xx；
2. 仅在"业务上成功，但需要提示轻微异常"的场景下才考虑返回 200 + 特定业务码。

### 问题 2：日志中看不到对应请求

**判断依据：**

1. 是否未在应用入口挂载 `loggerMiddleware`；
2. 是否有反向代理（如 Nginx）直接拦截了请求，后端根本未收到；
3. 过滤器或日志采集系统是否屏蔽了某些 level 或字段。

**处理建议：**

1. 确认 `app.use(loggerMiddleware);` 在所有路由之前；
2. 在本地环境直接访问后端端口绕过代理进行验证；
3. 在日志系统中临时放宽过滤条件，按时间窗口 + path 搜索。

### 问题 3：日志信息太多，难以定位关键错误

**判断依据：**

1. 是否大量打印调试日志（debug）或无意义的文本；
2. 是否把整个请求体/响应体直接序列化到日志中；
3. 是否缺少统一字段导致无法按 `status` / `error` 聚合。

**处理建议：**

1. 将临时调试日志明确标记并限制在开发环境使用；
2. 避免记录大对象，仅记录关键字段（如 `id`、`subject` 等）；
3. 始终保证错误日志包含 `type/status/code/error/path/method`，便于通过结构化查询筛选。

### 问题 4：错误消息对用户不友好

**判断依据：**

1. 错误文案是否存在英文/中文混杂、拼写错误、含糊其辞等问题；
2. 是否直接返回了内部异常信息（如数据库错误、第三方 API 报错原文）；
3. 是否与前端提示文案规范不一致。

**处理建议：**

1. 将面向用户的消息与日志中的详细错误区分对待；
2. 在错误处理中统一封装用户可见的 message，并在日志中记录更详细的错误上下文；
3. 在文档中维护常用错误码与中文说明对照表。

## 五、最佳实践案例

### 案例 1：登录成功场景

**场景描述：**  
用户通过 `/api/auth/login` 成功登录。

**期望行为：**

- 响应体：
  - HTTP 状态码：`200`
  - JSON: `{ code: 200, message: '登录成功', data: { ... }, timestamp }`
- 访问日志：
  - 包含 `method=POST`、`url=/api/auth/login`、`res.statusCode=200`、`responseTime` 等字段；
  - `type` 字段不存在（普通访问日志）。
- 错误日志：
  - 不应出现与该请求相关的 `app_error` / `validation_error` / `unknown_error`。

**判断要点：**

- 三方信息（响应 / 访问日志 / 错误日志）一致表明本次行为是"成功行动"；
- 如有测试用例，应同时验证 token 结构与用户信息字段。

### 案例 2：验证码错误场景

**场景描述：**  
用户在 `/api/auth/login` 提交错误验证码。

**期望行为：**

- 响应体：
  - HTTP 状态码：`400` 或 `422`（本项目约定为 400）；
  - JSON: `{ code: 400, message: '验证码错误', error: 'INVALID_CODE', timestamp }`（示意）。
- 访问日志：
  - `res.statusCode=400`；
  - 可通过 `req.id` 将该请求与错误日志关联。
- 错误日志：
  - 一条 `type='app_error'` 或 `type='validation_error'` 的日志；
  - `status=400`、`code=400`、`error='INVALID_CODE'`（或 `VALIDATION_ERROR`）；
  - `path='/api/auth/login'`、`method='POST'`。

**判断要点：**

- HTTP 层使用 4xx 表示客户端错误，避免误用 200/500；
- 错误码与文案清晰区分"验证码错误"与其他错误；
- 日志可用于区分大量验证码错误请求（便于风控/限流分析）。

### 案例 3：服务器内部错误场景

**场景描述：**  
某接口内部抛出未捕获的异常（例如第三方服务抖动）。

**期望行为：**

- 响应体：
  - HTTP 状态码：`500`；
  - JSON: `{ code: 500, message: '服务器内部错误', error: 'INTERNAL_SERVER_ERROR', timestamp }`。
- 错误日志：
  - `type='unknown_error'`、`status=500`、`code=500`、`error='INTERNAL_SERVER_ERROR'`；
  - `path`、`method`、`stack`（在开发/测试环境）；
  - 不包含敏感信息（如数据库连接字符串、访问令牌等）。

**判断要点：**

- 对外隐藏内部细节，仅用通用文案提示；
- 日志中保留足够的上下文和堆栈，以便开发者定位问题；
- 后续可根据错误日志频率配置告警规则。

## 六、小结与执行建议

1. 在日常开发与联调中，将"请求 → 响应 → 日志"三者作为一个整体来看待，而不是只看前端提示或只看数据库；
2. 为新增接口或改动接口时，优先考虑：
   - 预期的状态码 / 错误码 / 日志字段；
   - 是否会给测试和排查带来足够信息；
3. 在 Code Review 中，可以基于本方法论检查：
   - 是否正确抛出 `AppError` / 使用 `ZodError`；
   - 是否依赖错误中间件输出统一的错误响应与日志；
   - 是否有覆盖关键分支的单元测试。

通过在团队内统一执行以上判断步骤与标准，可以显著提升问题定位效率和日志质量，使"正确码/错误码 + 系统日志"成为可靠的诊断工具。
