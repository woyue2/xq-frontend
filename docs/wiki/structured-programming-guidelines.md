# 结构化编程与测试策略规范（后端/前端通用）

> 目的：为知识星球问答小程序项目提供一套可落地的结构化编程与测试策略规范，用于约束后续功能开发与缺陷修复的设计与实现方式。

## 一、模块化与分层设计

- 后端按三层划分：
  - 路由层（Controller）：负责 HTTP 请求解析、调用服务层、组装统一响应；
  - 服务层（Service）：承载业务流程与领域逻辑，只依赖仓储层和通用工具；
  - 数据访问层（Repository/Prisma）：封装数据库读写与查询。
- 横切基础设施：
  - 错误处理：统一使用 `AppError` + 错误中间件输出 `ApiResponse` 风格错误；
  - 日志：通过统一 logger 输出结构化日志（level + message + context）；
  - 校验：使用统一的参数校验方案（如 Zod schema）收敛输入检查逻辑。

## 二、结构化控制流

- 所有业务函数使用顺序、选择、循环三种基本结构组合实现：
  - 顺序：参数校验 → 权限检查 → 读取状态 → 更新状态 → 返回结果；
  - 选择：通过 `if/else` 或 `switch` 明确区分分支，而非隐式控制流；
  - 循环：使用 `for/for..of` 或数组高阶函数构建清晰循环，避免深层嵌套和多点早退。
- 禁止使用非结构化跳转模式：
  - 不在正常业务分支中依赖异常（throw）作为主要控制流；
  - 不引入等价于 `goto` 的嵌套回调或难以追踪的 Promise 链。

## 三、函数契约（前置条件 / 后置条件 / 异常）

- 为关键服务函数和路由 handler 约定统一的函数契约：
  - 前置条件（Preconditions）：入参与上下文假设（如必须已通过鉴权、参数非空、数据存在等）；
  - 后置条件（Postconditions）：返回值结构以及状态变化的保证（例如计数字段增减、日志已持久化）；
  - 异常情况（Exceptions）：会抛出的错误类型及含义（如 `AppError('QUESTION_NOT_FOUND')`）。
- 建议在 TypeScript 代码中使用 JSDoc/TSDoc 风格注释进行简要说明，并在方案包/设计文档中为关键路径集中列出。

## 四、统一错误处理与日志规范

- 错误处理：
  - 使用 `AppError` 表达业务错误，携带 HTTP 状态码、错误码、用户可见 message 以及可选 `bizCode`；
  - 所有错误统一通过错误中间件转换为 `{ code, message, error?, timestamp }` 格式响应；
  - 对外只暴露必要信息，避免泄露内部实现细节。
- 日志规范：
  - INFO：关键业务操作成功（创建问题、行为上报、点赞/收藏状态变更等）；
  - WARN：可恢复错误或边缘情况（例如参数缺失但可采用默认值处理）；
  - ERROR：未捕获异常或严重业务失败，记录堆栈及核心上下文（用户 ID、路由、部分参数）。

## 五、测试与覆盖率策略

- 单元测试：
  - 以分支路径为最小测试单元，确保每个条件分支至少有一个用例覆盖；
  - 优先为服务层与复杂路由编写单测，结合集成测试验证端到端行为。
- 覆盖率目标：
  - 对本迭代涉及的模块（如行为埋点、互动接口、通知模块）设定 branch/statement 覆盖率 ≥ 85%；
  - 将覆盖率报告纳入本地或 CI 检查，作为质量门槛之一。
- 前端测试：
  - 为 `src/services/api.ts` 中的核心 API 封装编写单元测试，验证成功路径与典型错误分支；
  - 结合类型检查（`npm run typecheck`）确保类型与后端合同一致。

## 六、文档与交付物

- 每个结构化方案包的实施应至少产出：
  - 结构化设计说明（模块划分、接口契约、控制流概述）；
  - 对应源代码改动（后端/前端）；
  - 单元/集成测试与覆盖率报告；
  - 部署与运行指南（包括环境变量、启动命令与测试执行方式）。
- 所有关键决策与规范更新需同步记录到 HelloAGENTS 知识库和 `helloagents/CHANGELOG.md` 中，保持"知识库即唯一事实来源"的目标。
