## 二、详细修复方案

### 🔴 P0：Behavior 模块伪批量实现和缺少sessionId

**问题编号**: B-01
**严重程度**: 🔴 严重
**影响**: 性能差、功能不完整

#### 问题描述

1. **伪批量实现**: 前端 `behaviorService.batchLog` 方法声称支持批量上传，实际是循环调用单条接口，导致：
   - N次HTTP请求而非1次
   - 串行等待，延迟累积
   - 流量开销N倍

2. **缺少sessionId**: 前端调用 `behaviorService.log` 时未传递 `sessionId` 参数，后端虽然支持但从未收到，无法进行会话内行为序列分析。

#### 修复方案

**Task B-01.1：后端实现真正的批量接口**

- 文件: `backend/src/routes/behavior.routes.ts` (新建或扩展)
- 实现: 新增 `POST /behavior/log/batch` 接口
- 请求体:
  ```typescript
  {
    events: Array<{
      type: string;
      timestamp?: number;
      metadata?: any;
      sessionId?: string;
    }>
  }
  ```
- 响应体:
  ```typescript
  {
    successCount: number;
    failedCount: number;
    results: Array<{
      index: number;
      logId?: string;
      error?: string;
    }>
  }
  ```
- 实现要点:
  - 批量插入数据库，使用事务
  - 验证每个事件的类型和长度
  - 部分成功原则：即使某些事件失败，不影响其他事件处理
  - 返回每个事件的处理结果

**Task B-01.2：前端更新batchLog使用批量接口**

- 文件: `src/services/api.ts`
- 修改: `behaviorService.batchLog` 改为调用新批量接口
- 实现:
  ```typescript
  batchLog: async (events: BehaviorLogParams[]) => {
    const { data } = await api.post<ApiResponse<{
      successCount: number;
      failedCount: number;
      results: Array<{ index: number; logId?: string; error?: string }>;
    }>>('/behavior/log/batch', { events });
    return data.data;
  }
  ```

**Task B-01.3：前端log方法添加sessionId参数**

- 文件: `src/services/api.ts`
- 修改: `behaviorService.log` 签名和调用
- 实现:
  ```typescript
  export interface BehaviorLogParams {
    type: string;
    timestamp?: number;
    metadata?: Record<string, unknown>;
    sessionId?: string;  // 新增
  }

  export const behaviorService = {
    log: async (params: BehaviorLogParams) => {
      const { type, timestamp = Date.now(), metadata, sessionId } = params;
      const { data } = await api.post<ApiResponse<{ logId: string }>>('/behavior/log', {
        type,
        timestamp,
        metadata,
        sessionId  // 传递 sessionId
      });
      return data.data;
    },
    // ...
  };
  ```
- 调用点更新: 在所有调用 `behaviorService.log` 的地方，根据需要传递 `sessionId`（如从路由或store获取）

**Task B-01.4：添加类型定义**

- 文件: `src/types/api.ts`
- 添加:
  ```typescript
  export interface BehaviorLogParams {
    type: string;
    timestamp?: number;
    metadata?: Record<string, unknown>;
    sessionId?: string;
  }

  export interface BehaviorLogResult {
    logId: string;
  }

  export interface BehaviorBatchResult {
    successCount: number;
    failedCount: number;
    results: Array<{
      index: number;
      logId?: string;
      error?: string;
    }>;
  }
  ```

#### 验收标准
- ✅ 批量接口一次上传所有事件，性能显著提升
- ✅ sessionId 正确传递并存储到数据库
- ✅ 类型定义完整，TypeScript 编译无错误
- ✅ 现有调用点已适配新签名

### 🟡 P1：Interaction 模块 LikePayload.targetType 类型范围不一致

**问题编号**: I-01
**严重程度**: 🟡 中等
**影响**: 类型误导、运行时错误

#### 问题描述

前端 `LikePayload.targetType` 定义为 `'question' | 'answer'`，但后端路由层只支持 `'question'`，如果前端传递 `'answer'` 会返回400错误。类型定义过于宽松，编译时无法发现错误。

#### 修复方案

**Task I-01.1：收紧 LikePayload.targetType 类型**

- 文件: `src/types/api.ts`
- 修改: 将 `targetType` 从联合类型改为字面量 `'question'`
- 实现:
  ```typescript
  // 修改前
  export interface LikePayload {
    targetType: 'question' | 'answer';  // ❌ 过于宽松
    targetId: string;
    action: 'like' | 'unlike';
  }

  // 修改后
  export interface LikePayload {
    targetType: 'question';  // ✅ 收紧
    targetId: string;
    action: 'like' | 'unlike';
  }
  ```

**Task I-01.2：更新 interactionService 实现**

- 文件: `src/services/api.ts`
- 检查: `interactionService.like` 方法
- 确认: 已硬编码 `targetType: 'question'`，无需修改
- 验证: 移除对 `payload.targetType` 的检查（如果存在）

#### 验收标准
- ✅ 类型定义准确反映后端能力
- ✅ 编译时阻止传递错误的 targetType
- ✅ 所有调用点使用正确的 targetType

### 🟡 P1：Audit 模块 PendingQuestion 缺少 images 字段

**问题编号**: A-01
**严重程度**: 🟡 中等
**影响**: 审核页面无法显示问题图片

#### 问题描述

后端 `auditService.listPending` 返回的待审核问题对象包含 `images: []` 字段（当前为空数组），但前端 `PendingQuestion` 类型未定义此字段，导致无法在类型层面获取图片信息。

#### 修复方案

**Task A-01.1：前端 PendingQuestion 类型添加 images 字段**

- 文件: `src/types/api.ts`
- 修改: 在 `PendingQuestion` 接口中添加 `images` 字段
- 实现:
  ```typescript
  export interface PendingQuestion {
    id: string;
    type: 'question';
    title: string;
    content: string;
    images: string[];  // ✅ 添加
    authorId: string;
    authorName: string;
    status: string;
    aiResult: string | null;
    createdAt: string;
  }
  ```

**Task A-01.2：后端确认 images 字段的语义**

- 文件: `backend/src/services/audit.service.ts`
- 检查: `listPending` 方法中 `images: []` 的含义
- 决策:
  - 如果未来支持问题图片，应返回实际的 `q.images`
  - 如果暂时不支持，保持返回空数组，但前端类型应包含此字段以保持一致性
- 建议: 当前保持空数组，但类型对齐

#### 验收标准
- ✅ PendingQuestion 类型包含 images 字段
- ✅ 审核页面可以访问 `question.images`（即使为空）
- ✅ 类型检查通过

### 🟢 P2：Audit 模块 PendingQuestion 的 images 字段冗余

**问题编号**: A-02
**严重程度**: 🟢 轻微
**影响**: 带宽浪费、数据冗余

#### 问题描述

后端 `auditService.listPending` 对问题审核返回 `images: []` 始终为空数组，因为当前问题表不存储图片（图片在创建时已单独处理）。这是一个冗余字段。

#### 修复方案

**Task A-02.1：后端移除 PendingQuestion 的 images 字段**

- 文件: `backend/src/services/audit.service.ts`
- 修改: 在 `listPending` 的映射中移除 `images: []`
- 实现:
  ```typescript
  // 修改前
  list: list.map((q) => ({
    id: q.id,
    type: 'question' as const,
    title: q.title,
    content: q.content ?? '',
    images: [],  // ❌ 移除
    authorId: q.authorId,
    // ...
  }))

  // 修改后
  list: list.map((q) => ({
    id: q.id,
    type: 'question' as const,
    title: q.title,
    content: q.content ?? '',
    authorId: q.authorId,
    // ✅ 不包含 images
  }))
  ```

**Task A-02.2：前端 PendingQuestion 类型 images 改为可选**

- 文件: `src/types/api.ts`
- 修改: 将 `images` 字段改为可选
- 实现:
  ```typescript
  export interface PendingQuestion {
    id: string;
    type: 'question';
    title: string;
    content: string;
    images?: string[];  // ✅ 改为可选
    authorId: string;
    // ...
  }
  ```

#### 验收标准
- ✅ 后端响应不再包含空的 images 数组
- ✅ 前端类型允许 images 缺失
- ✅ 审核页面代码能处理 images 不存在的情况

### 🟢 P2：Notification 模块 userId 字段一致性确认

**问题编号**: N-01
**严重程度**: 🟢 轻微
**影响**: 类型完整性

#### 问题描述

文档中对 `Notification.userId` 字段存在矛盾：
- 文档4.0: 认为 userId 是前端冗余（后端不返回）
- 文档11.0: 认为 userId 是前端缺失（应该返回）
- 当前代码: 前端类型有 userId，后端 `notification.routes.ts` 使用 `findMany` 会查询 userId 但响应映射中未明确返回

需要确认实际状态并统一。

#### 修复方案

**Task N-01.1：检查后端 Notification 路由返回**

- 文件: `backend/src/routes/notification.routes.ts`
- 检查: `listForUser` 和 `findById` 的响应映射
- 确认: 是否在 `select` 或 `map` 中返回了 `userId`

**Task N-01.2：根据后端实际行为调整前端类型**

- 如果后端返回 `userId`:
  - 前端 `Notification` 类型中 `userId` 应为必填 `string`
- 如果后端不返回 `userId`:
  - 前端 `Notification` 类型中 `userId` 应为可选 `string?` 或移除
- 建议: 由于通知天然属于用户，前端通常从用户上下文获取，`userId` 可以保持可选或移除

#### 验收标准
- ✅ 前后端对 userId 的约定一致
- ✅ 类型定义准确反映实际数据流
