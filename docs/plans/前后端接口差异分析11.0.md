### 问题 116：前端 Notification 类型缺少 userId 字段

**优先级**: 低

**问题描述**:
后端 `notification` 数据库表和查询结果包含 `userId` 字段（通知归属用户），但前端 `Notification` 类型定义中没有包含此字段。虽然前端在获取通知列表时不需要使用 `userId`（从当前登录用户角度获取），但作为完整的类型定义应该保持字段完整。

**后端现状**:
```typescript
// backend/src/services/notification.service.ts
async listForUser(params: {
  userId: string;
  page?: number;
  limit?: number;
  unreadOnly?: boolean;
}) {
  // ...
  const [notifications, total, unreadCount] = await Promise.all([
    prisma.notification.findMany({
      where,
      // ... 返回字段包含 userId
    }),
    // ...
  ]);

  return {
    notifications,  // ✅ 包含 userId
    total,
    unreadCount
  };
}
```

**前端现状**:
```typescript
// src/types/api.ts
export interface Notification {
    id: string;
    type: string;
    title: string;
    content?: string;
    targetType?: string;
    targetId?: string;
    isRead: boolean;
    readAt?: string;
    createdAt: string;
    // ❌ 缺少 userId
}
```

**修复建议**:
```typescript
// 前端添加 userId 字段
export interface Notification {
    id: string;
    userId: string;  // ✅ 添加
    type: string;
    title: string;
    content?: string;
    targetType?: string;
    targetId?: string;
    isRead: boolean;
    readAt?: string;
    createdAt: string;
}
```

### 问题 117：前端 markAsRead 缺少参数类型定义

**优先级**: 中

**问题描述**:
前端 `notificationService.markAsRead` 方法直接使用 `ids: string[]` 作为参数类型，但后端 `/notifications/read` 接口对参数有更详细的验证逻辑。前端缺少对应的请求类型定义，无法在编译期发现参数错误。

**后端现状**:
```typescript
// backend/src/routes/notification.routes.ts
notificationRouter.post(
  '/notifications/read',
  authMiddleware,
  async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    try {
      const body = req.body as any;
      const idsRaw = body?.ids;

      if (!Array.isArray(idsRaw) || idsRaw.length === 0) {
        throw new AppError(400, 'VALIDATION_ERROR', '参数验证失败', {
          errors: [
            {
              field: 'ids',
              message: 'ids 必须为非空字符串数组'
            }
          ]
        });
      }

      const ids = idsRaw.map((id) => String(id));
      // ...
    } catch (err) {
      next(err);
    }
  }
);
```

**前端现状**:
```typescript
// src/services/api.ts
markAsRead: async (ids: string[]) => {
    const { data } = await api.post<ApiResponse<{ success: boolean; updatedCount: number }>>(
        '/notifications/read',
        { ids }
    );
    return data.data;
},
// ❌ 缺少参数类型定义和验证
```

**修复建议**:
```typescript
// 前端添加参数类型定义
export interface MarkAsReadPayload {
    ids: string[];
}

export interface MarkAsReadResponse {
    success: boolean;
    updatedCount: number;
}

// 在 notificationService 中使用
markAsRead: async (payload: MarkAsReadPayload) => {
    const { data } = await api.post<ApiResponse<MarkAsReadResponse>>(
        '/notifications/read',
        payload
    );
    return data.data;
},
```

### 问题 118：前端 Notification 类型缺少 type 枚举定义

**优先级**: 低

**问题描述**:
前端 `Notification` 类型中 `type` 字段使用 `string` 类型，但后端通知系统有预定义的通知类型（如系统通知、问题被回答、回答被点赞等）。缺少类型枚举定义会导致前端无法进行类型安全的类型判断。

**后端现状**:
```typescript
// backend/src/services/notification.service.ts
// 通知类型定义（示例）
type NotificationType = 
  | 'system'
  | 'question_answered'
  | 'answer_liked'
  | 'comment_received'
  | 'answer_accepted';

// 创建通知示例
async create(data: {
  userId: string;
  type: NotificationType;
  title: string;
  content?: string;
  targetType?: string;
  targetId?: string;
}) {
  return prisma.notification.create({ data });
}
```

**前端现状**:
```typescript
// src/types/api.ts
export interface Notification {
    id: string;
    type: string;  // ❌ 缺少类型枚举
    title: string;
    content?: string;
    targetType?: string;
    targetId?: string;
    isRead: boolean;
    readAt?: string;
    createdAt: string;
}

// 使用时无法进行类型安全的类型判断
const getNotificationIcon = (type: string) => {  // ❌ 无法利用类型系统
    switch (type) {
        case 'question_answered':
            return 'answer';
        case 'answer_liked':
            return 'like';
        default:
            return 'system';
    }
};
```

**修复建议**:
```typescript
// 前端添加通知类型枚举
export type NotificationType = 
    | 'system'
    | 'question_answered'
    | 'answer_liked'
    | 'comment_received'
    | 'answer_accepted'
    | string;  // 保留兼容性

export interface Notification {
    id: string;
    type: NotificationType;  // ✅ 使用类型枚举
    title: string;
    content?: string;
    targetType?: string;
    targetId?: string;
    isRead: boolean;
    readAt?: string;
    createdAt: string;
}

// 使用时可以进行类型安全的类型判断
const getNotificationIcon = (type: NotificationType) => {
    switch (type) {
        case 'question_answered':
            return 'answer';
        case 'answer_liked':
            return 'like';
        default:
            return 'system';
    }
};
```

### 问题 119：后端返回字段与前端类型定义差异

**优先级**: 低

**问题描述**:
后端 `listForUser` 和 `findById` 方法返回的通知对象包含所有数据库字段，但前端 `Notification` 类型只定义了部分字段。这种差异在 TypeScript 严格模式下可能导致类型不匹配警告。

**后端现状**:
```typescript
// backend/src/services/notification.service.ts
async listForUser(params) {
  const [notifications, total, unreadCount] = await Promise.all([
    prisma.notification.findMany({
      where,
      orderBy: { createdAt: 'desc' },
      skip: (page - 1) * limit,
      take: limit
    }),
    // ...
  ]);

  return {
    notifications,  // 返回完整 Prisma 对象
    total,
    unreadCount
  };
}

// route 层映射到响应
notifications: notifications.map((n) => ({
    id: n.id,
    type: n.type,
    title: n.title,
    content: n.content,
    targetType: n.targetType,
    targetId: n.targetId,
    isRead: n.isRead,
    readAt: n.readAt,
    createdAt: n.createdAt
    // ❌ 缺少 userId
}))
```

**前端现状**:
```typescript
// src/types/api.ts
export interface Notification {
    id: string;
    userId?: string;  // ❌ 可选类型，与后端不一致
    type: string;
    title: string;
    content?: string;
    targetType?: string;
    targetId?: string;
    isRead: boolean;
    readAt?: string;
    createdAt: string;
}

// src/services/api.ts
const { data } = await api.get<
    ApiResponse<{
        notifications: Notification[];
        unreadCount: number;
        total: number;
    }>
>('/notifications', { params: queryParams });
```

**问题分析**:
- 后端 route 层没有返回 `userId`，但 `notificationService.listForUser` 返回的 Prisma 对象包含 `userId`
- 前端 `Notification.userId` 定义为可选 `?`，与后端返回的实际值不完全匹配
- 这种差异不会导致运行时错误，但影响类型完整性

**修复建议**:
```typescript
// 方案1：后端 route 层添加 userId 返回
notifications: notifications.map((n) => ({
    id: n.id,
    userId: n.userId,  // ✅ 添加
    type: n.type,
    title: n.title,
    content: n.content,
    targetType: n.targetType,
    targetId: n.targetId,
    isRead: n.isRead,
    readAt: n.readAt,
    createdAt: n.createdAt
}))

// 方案2：前端 userId 改为必填
export interface Notification {
    id: string;
    userId: string;  // ✅ 改为必填
    type: string;
    title: string;
    content?: string;
    targetType?: string;
    targetId?: string;
    isRead: boolean;
    readAt?: string;
    createdAt: string;
}
```

### 问题 120：前端缺少批量获取通知详情的能力

**优先级**: 低

**问题描述**:
前端 `notificationService` 只提供了单个通知详情获取方法 `getNotificationById`，但在通知列表页面可能需要批量获取多个通知的详细信息。后端 API 设计为 RESTful 单个获取，如果需要批量功能需要额外实现。

**前端现状**:
```typescript
// src/services/api.ts
export const notificationService = {
    getNotifications: async (params: { page?: number; limit?: number; unread?: boolean }) => {
        // 获取通知列表
        // ...
    },
    getNotificationById: async (id: string) => {
        // ✅ 只支持单个获取
        const { data } = await api.get<ApiResponse<Notification>>(
            `/notifications/${id}`
        );
        return data.data;
    },
    // 缺少 batchGetNotifications
};
```

**后端现状**:
```typescript
// backend/src/routes/notification.routes.ts
// 只提供了单个通知详情获取
notificationRouter.get(
  '/notifications/:id',
  // ...
);
```

**问题分析**:
这是一个功能增强建议，而非前后端不一致问题。当前设计下，前端在通知列表中已经可以获取 `title`、`content` 等基本信息，通常不需要额外请求详情。

**修复建议**:
```typescript
// 前端添加批量获取方法（可选）
interface BatchGetNotificationsResponse {
    notifications: Notification[];
    notFoundIds: string[];
}

export const notificationService = {
    // ... 现有方法

    // 新增：批量获取通知详情
    batchGetNotifications: async (ids: string[]): Promise<BatchGetNotificationsResponse> => {
        const { data } = await api.post<ApiResponse<BatchGetNotificationsResponse>>(
            '/notifications/batch',
            { ids }
        );
        return data.data;
    }
};

// 如果需要后端支持批量接口
// backend/src/routes/notification.routes.ts
notificationRouter.post(
  '/notifications/batch',
  authMiddleware,
  async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    try {
      const { ids } = req.body as { ids: string[] };
      
      const notifications = await prisma.notification.findMany({
        where: {
          id: { in: ids },
          userId: req.user.id  // 只返回属于自己的通知
        }
      });

      const foundIds = new Set(notifications.map(n => n.id));
      const notFoundIds = ids.filter(id => !foundIds.has(id));

      return res.json({
        code: 200,
        message: 'success',
        data: {
          notifications,
          notFoundIds
        },
        timestamp: Date.now()
      });
    } catch (err) {
      next(err);
    }
  }
);
```

## 优化建议

### 短期优化（高优先级）

1. **统一 userId 字段处理**: 后端 route 层返回 userId，前端类型改为必填
2. **添加 markAsRead 参数类型定义**: 创建 MarkAsReadPayload 类型

### 中期优化（中优先级）

1. **添加 NotificationType 枚举**: 定义后端支持的通知类型
2. **添加批量获取通知方法**: 支持批量获取通知详情（可选）

### 长期优化（低优先级）

1. **添加通知订阅/取消订阅**: 支持用户订阅特定类型的通知
2. **添加通知图标和跳转信息**: 在通知对象中直接包含目标页面路由信息

---

## 总结

notification（通知）模块整体功能完整，前后端一致性较好。主要发现以下问题：

1. **后端 route 层未返回 userId**: 虽然数据存在，但响应中没有返回
2. **前端缺少参数类型定义**: markAsRead 等方法缺少类型约束
3. **缺少通知类型枚举**: type 字段使用 string 类型，无法进行类型安全判断
4. **缺少批量获取能力**: 如需批量获取需要额外实现

建议按优先级逐步修复，确保各接口返回的数据结构一致，提升前端开发体验和数据可预测性。

## 优化建议

### 短期优化（高优先级）

1. **补充 WhitelistUser 完整字段**: 添加 `updatedAt`、`registeredAt` 的 null 可能性质
2. **统一 searchField 参数传递**: 确保前端调用时传递 searchField 参数

### 中期优化（中优先级）

1. **修正 registeredAt 类型**: 改为 `string | null`
2. **确保 createdBy 在返回值中存在**: 在 addToWhitelist 返回类型中明确

### 长期优化（低优先级）

1. **添加批量操作接口**: 支持批量导入白名单
2. **添加导出功能**: 支持导出白名单数据

## 总结

whitelist（白名单）模块整体功能完整，但存在以下问题：

1. **WhitelistUser 类型缺少 updatedAt 字段**（高优先级）
2. **registeredAt 类型不准确**（应为 `string | null`）
3. **searchField 参数前端调用处可能未传递**
4. **createdBy 字段在某些返回值中可能不存在**
5. **缺少批量导入和导出功能**

建议按优先级逐步修复，确保各接口返回的数据结构一致，提升前端开发体验和数据可预测性。
