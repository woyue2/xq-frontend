## 概述

## 一、question.api.spec.ts - Q-API-005P 分页参数验证失败

### 问题描述
期望：非法分页参数（`page=0`、`pageSize=0`、`page=abc`）返回 400  
实际：返回 200（自动修正为默认值）

### 根本原因
`question.service.ts:214-215` 采用自动修正策略，不抛出错误：
```typescript
const safePage = (Number.isInteger(rawPage) && rawPage > 0) ? rawPage : 1;
const safePageSize = (Number.isInteger(rawPageSize) && rawPageSize > 0) ? Math.min(rawPageSize, 100) : 20;
```

### 推荐方案：配置化严格验证
- **改动范围**：在 `list()` 方法中增加环境变量 `PAGINATION_STRICT_VALIDATION` 控制
- **实现**：
  - 当 `PAGINATION_STRICT_VALIDATION=true` 时，对非法参数抛出 `AppError(400, 'INVALID_PAGINATION')`
  - 当 `false`（默认）时，保持现有自动修正行为
- **风险点**：测试环境启用严格验证后，可能影响依赖自动修正的前端代码
- **影响**：向后兼容，通过配置切换；需修改服务层逻辑

## 二、subject.api.spec.ts - 配置接口 404

### 问题描述
`GET /api/config/subjects` 返回 404

### 根本原因
路由路径不匹配：
- 实际定义：`/api/config/question-dimensions`（`config.routes.ts:8`）
- 测试请求：`/api/config/subjects`

### 推荐方案：添加别名路由
- **改动范围**：在 `config.routes.ts` 中新增路由
- **实现**：
  ```typescript
  // 新增别名路由，向后兼容
  configRouter.get(
    '/subjects',
    async (req, res, next) => {
      // 直接调用现有服务，返回相同数据结构
      const dimensions = await questionDimensionService.getPublicDimensions();
      return res.json({
        code: 200,
        message: 'success',
        data: { subjects: dimensions }, // 字段名适配
        timestamp: Date.now()
      });
    }
  );
  ```
- **风险点**：维护两个路径，需确保数据一致性
- **影响**：新旧路径都可用；增加少量代码但风险低

## 三、auth.api.spec.ts - 注册失败

### 问题描述
AUTH-API-005 注册用户失败（具体错误未明确）

### 可能原因（高概率）
1. 验证码验证失败（固定码 `'123456'` 无效）
2. 白名单检查失败（`userWhitelist` 无记录）
3. 数据库唯一约束冲突（phone 重复）

### 推荐方案：测试环境特殊配置 + 唯一数据
- **改动范围**：测试层
- **实现**：
  1. **环境变量配置**（`.env.test` 或测试启动脚本）：
     ```
     AUTH_FORCE_RANDOM_CODE=false
     AUTH_STRICT_WHITELIST_FOR_LOGIN=false
     NODE_ENV=test
     ```
  2. **测试数据准备**：
     - 在 `beforeEach` 中预创建 `userWhitelist` 记录（包含测试手机号）
     - 使用唯一生成的手机号（如带时间戳：`136${Date.now()}`）
  3. **验证码流程**：
     - 先调用 `POST /api/auth/send-code` 发送验证码
     - 使用返回的验证码或固定码 `'123456'` 进行注册
- **风险点**：测试环境与生产环境差异大，可能无法发现生产问题
- **影响**：简化测试，提高稳定性；需维护测试环境配置

## 四、profile-my-answers.api.spec.ts - 唯一约束冲突

### 问题描述
创建用户时违反唯一约束（phone 字段）

### 根本原因
- 使用固定电话号码 `'13900006666'`
- `beforeEach` 删除不彻底或并发执行导致冲突

### 推荐方案：唯一生成测试数据
- **改动范围**：测试层
- **实现**：
  ```typescript
  // 将固定 ID 和 phone 改为动态生成
  const teacherId = `profile_teacher_${Date.now()}`;
  const teacherPhone = `139${Date.now().toString().slice(-8)}`;
  ```
- **风险点**：需修改测试用例中的硬编码引用
- **影响**：从根本上避免冲突，是最稳健的方案

## 五、验收步骤是否需要修改？

### 回答：**需要，但不影响核心验收流程**

#### 原因分析

1. **分页验证配置**：
   - 验收应在**生产环境配置**下进行（`PAGINATION_STRICT_VALIDATION` 应与生产一致）
   - 如果生产环境保持自动修正（`false`），则验收时不应测试非法参数返回 400
   - **验收调整**：如果产品要求严格验证，则验收需新增"非法分页参数返回 400"的测试用例

2. **配置接口路径**：
   - 新增 `/api/config/subjects` 别名后，验收时应使用**产品文档规定的路径**
   - 如果产品文档指定使用 `/api/config/subjects`，则验收用例路径正确，无需修改
   - 如果产品文档未明确，验收应覆盖**两个路径**，确保向后兼容

3. **注册与数据清理**：
   - 推荐的测试环境配置**仅用于自动化测试**，验收应在**真实生产/预发环境**进行
   - 生产环境不会降级，白名单、验证码、唯一约束等检查都是严格的
   - **验收调整**：验收前需确保预发环境已预置白名单数据，并使用真实验证码流程

4. **唯一数据生成**：
   - 这是测试框架层面的改进，**不影响验收操作步骤**
   - 验收时使用真实业务数据（如手动创建测试账号），不依赖自动化测试的数据生成逻辑

## 六、执行顺序建议

1. **第一阶段：测试框架改进**
   - 修改测试数据生成逻辑（唯一 ID 和 phone）
   - 添加测试环境配置（`.env.test`）
   - 验证 4 个失败用例全部通过

2. **第二阶段：代码修复**
   - 实现分页严格验证配置（`PAGINATION_STRICT_VALIDATION`）
   - 添加 `/api/config/subjects` 别名路由
   - 验证测试通过且不影响现有功能

3. **第三阶段：验收准备**
   - 更新验收文档（`模块验收.md`、`模块验收操作指南.md`）
   - 在预发环境验证核心链路
   - 确认配置项与生产环境一致

## 七、风险提示

1. **配置化策略**：环境变量过多可能导致运维复杂度增加，建议集中管理（如 `config/` 目录）
2. **别名路由**：长期维护两个路径可能产生分歧，建议在 v2.0 版本移除旧路径 `/api/config/question-dimensions`
3. **测试降级**：测试环境的特殊配置应明确标注，避免误导新成员认为生产环境也如此
4. **验收差异**：验收环境与测试环境的行为差异需在文档中明确说明，避免验收时产生困惑
