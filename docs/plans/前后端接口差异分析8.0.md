## 发现的问题

### 问题 76：后端缺少通知详情接口

**优先级**: 中

**问题描述**:
当前只提供了通知列表接口 `/notifications`，没有获取单个通知详情的接口。前端在某些场景下可能需要查看通知的完整信息。

**后端现状**:
```typescript
// backend/src/routes/notification.routes.ts
// 现有接口：
// - GET /notifications - 获取通知列表
// - GET /notifications/unread-count - 获取未读数量
// - POST /notifications/read - 标记通知已读
```

**前端现状**:
```typescript
// src/pages/NotificationsPage.tsx
// 通过列表接口获取通知信息
const { notifications, unreadCount: unread, total } =
  await notificationService.getNotifications({ page: 1, limit: 20 });
```

**修复建议**:
```typescript
// 后端添加通知详情接口
notificationRouter.get(
  '/notifications/:id',
  authMiddleware,
  async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    try {
      const { id } = req.params;
      const notification = await notificationService.findById(id);

      if (!notification || notification.userId !== req.user?.id) {
        throw new AppError(404, 'NOT_FOUND', '通知不存在');
      }

      return res.json({
        code: 200,
        message: 'success',
        data: {
          id: notification.id,
          type: notification.type,
          title: notification.title,
          content: notification.content,
          targetType: notification.targetType,
          targetId: notification.targetId,
          isRead: notification.isRead,
          createdAt: notification.createdAt
        },
        timestamp: Date.now()
      });
    } catch (err) {
      next(err);
    }
  }
);
```

### 问题 77：后端缺少批量标记所有通知已读专用接口

**优先级**: 中

**问题描述**:
前端 `NotificationsPage.tsx` 中的 `handleMarkAllRead` 函数通过调用 `markAsRead(ids)` 批量标记未读通知为已读。该实现虽然可行，但效率较低（需要先获取所有未读通知 ID），且缺少专门的批量操作接口。

**后端现状**:
```typescript
// backend/src/routes/notification.routes.ts
// POST /notifications/read 接收 ids 数组
notificationRouter.post(
  '/notifications/read',
  authMiddleware,
  async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    const body = req.body as any;
    const idsRaw = body?.ids;
    // ... 验证和处理逻辑
  }
);
```

**前端现状**:
```typescript
// src/pages/NotificationsPage.tsx
const handleMarkAllRead = async () => {
  const ids = items.filter((n) => !n.isRead).map((n) => n.id);
  if (ids.length === 0) return;
  try {
    await notificationService.markAsRead(ids);
    // ...
  }
};
```

**修复建议**:
```typescript
// 后端添加标记所有通知已读接口
notificationRouter.post(
  '/notifications/read-all',
  authMiddleware,
  async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    try {
      if (!req.user) {
        throw new AppError(401, 'UNAUTHORIZED', '未登录');
      }

      const result = await notificationService.markAllAsRead({
        userId: req.user.id
      });

      return res.json({
        code: 200,
        message: 'success',
        data: {
          success: true,
          updatedCount: result.updatedCount
        },
        timestamp: Date.now()
      });
    } catch (err) {
      next(err);
    }
  }
);

// service 添加 markAllAsRead 方法
async markAllAsRead(params: { userId: string }) {
  const result = await prisma.notification.updateMany({
    where: {
      userId: params.userId,
      isRead: false
    },
    data: {
      isRead: true
    }
  });

  return {
    updatedCount: result.count
  };
}

// 前端更新
const handleMarkAllRead = async () => {
  try {
    await notificationService.markAllAsRead();
    // ...
  }
};
```

### 问题 78：后端缺少删除通知接口

**优先级**: 低

**问题描述**:
当前系统没有提供删除通知的接口。用户积累的旧通知可能需要清理，但只能通过标记已读处理，无法真正删除。

**修复建议**:
```typescript
// 后端添加删除通知接口
notificationRouter.delete(
  '/notifications/:id',
  authMiddleware,
  async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    try {
      const { id } = req.params;
      const notification = await notificationService.findById(id);

      if (!notification || notification.userId !== req.user?.id) {
        throw new AppError(404, 'NOT_FOUND', '通知不存在');
      }

      await notificationService.deleteById(id);

      return res.json({
        code: 200,
        message: 'success',
        data: { success: true },
        timestamp: Date.now()
      });
    } catch (err) {
      next(err);
    }
  }
);

// service 添加 deleteById 方法
async deleteById(id: string) {
  return prisma.notification.delete({
    where: { id }
  });
}
```

### 问题 79：Notification 类型缺少 readAt 字段

**优先级**: 低

**问题描述**:
当前 Notification 类型只有 `isRead: boolean` 标记是否已读，没有记录用户何时阅读该通知。`readAt` 字段可用于后续的数据分析和通知偏好优化。

**修复建议**:
```typescript
// 后端 Prisma schema 添加 readAt 字段
model Notification {
  id         String   @id @default(cuid())
  userId     String
  type       String
  title      String
  content    String?
  targetType String?
  targetId   String?
  isRead     Boolean  @default(false)
  readAt     DateTime? // 新增：标记已读时间
  createdAt  DateTime @default(now())

  @@index([userId])
}

// 后端返回数据添加 readAt
notifications: notifications.map((n) => ({
  id: n.id,
  type: n.type,
  title: n.title,
  content: n.content,
  targetType: n.targetType,
  targetId: n.targetId,
  isRead: n.isRead,
  readAt: n.readAt, // 新增
  createdAt: n.createdAt
})),

// 前端类型定义添加 readAt
export interface Notification {
  id: string;
  type: string;
  title: string;
  content?: string;
  targetType?: string;
  targetId?: string;
  isRead: boolean;
  readAt?: string; // 新增
  createdAt: string;
}

// service markAsRead 时更新 readAt
async markAsRead(params: { userId: string; ids: string[] }) {
  const { userId, ids } = params;
  const where: any = { userId, isRead: false };
  if (ids.length > 0) {
    where.id = { in: ids };
  }

  const result = await prisma.notification.updateMany({
    where,
    data: {
      isRead: true,
      readAt: new Date()
    }
  });

  return { updatedCount: result.count };
}
```

### 问题 80：ChildInfo 类型缺少 realName 字段定义

**优先级**: 中

**问题描述**:
后端 `getChildren` 方法返回的数据中包含 `realName` 字段（来自 User 表的 name 字段），但前端 `ChildInfo` 类型没有定义该字段，导致类型不完整。

**后端现状**:
```typescript
// backend/src/services/parent.service.ts
async getChildren(parentId: string) {
  const relations = await prisma.parentChild.findMany({
    where: { parentId },
    include: {
      child: {
        select: {
          id: true,
          name: true,           // 真实姓名
          nickname: true,
          avatar: true,
          role: true,
          school: true,
          grade: true
        }
      }
    }
  });

  return relations.map((r) => ({
    ...r.child,
    name: r.child.nickname,      // 显示用的name（来自nickname）
    realName: r.child.name       // 真实姓名（可选）
  }));
}
```

**前端现状**:
```typescript
// src/types/parent.ts
export interface ChildInfo {
  id: string;
  name: string;
  grade: string;
  age: number;
  school?: string;
  avatar?: string;
  boundAt: string;
  lastActiveAt?: string;
  parentId: string;
}
// 缺少 realName 字段
```

**修复建议**:
```typescript
// 前端 ChildInfo 类型添加 realName 字段
export interface ChildInfo {
  id: string;
  name: string;        // 显示用的名字（来自nickname）
  realName?: string;   // 真实姓名（来自User.name）
  grade: string;
  age?: number;        // 后端未返回，改为可选
  school?: string;
  avatar?: string;
  boundAt?: string;   // 后端未返回，改为可选
  lastActiveAt?: string;
  parentId: string;
}
```

```typescript
// 后端修改 getChildren 方法，返回绑定时间
async getChildren(parentId: string) {
```

### 问题 84：bindChild 响应结构不完整

**优先级**: 中

**问题描述**:
后端 `bindChild` 方法直接返回被绑定的孩子用户对象，但前端期望的 `BindChildResponse` 结构包含 `child` 字段。实际实现中后端返回的就是 child 对象本身，不是 `{ child: ... }` 结构。

**后端现状**:
```typescript
// backend/src/services/parent.service.ts
async bindChild(...) {
  // ...
  return child;  // 直接返回 User 对象
}

// backend/src/routes/parent.routes.ts
const result = await parentService.bindChild(req.user.id, {
  phone, code, childName, school
});
res.json({
  code: 200,
  message: 'success',
  data: result  // result 就是 child 对象
});
```

**前端现状**:
```typescript
// src/types/parent.ts
export interface BindChildResponse {
  child: ChildInfo;
}

// src/services/parentService.ts
bindChild: (data: BindChildPayload) =>
  api.post<ApiResponse<ChildInfo>>('/parent/bind', data),
  // 期望返回的是 ChildInfo，不是 { child: ChildInfo }
```

**修复建议**:
```typescript
// 方案1：前端修改类型定义
export type BindChildResponse = ChildInfo;  // 直接是 ChildInfo

// 方案2：后端修改返回结构（推荐）
res.json({
  code: 200,
  message: 'success',
  data: {
    child: {
      id: child.id,
      name: child.nickname,
      // ... 其他字段
    }
  }
});
```

## 发现的问题

### 问题 85：LoginResponse.User 缺少 expiresAt 字段

**优先级**: 高

**问题描述**:
后端 `login` 和 `passwordLogin` 方法返回的 user 对象中包含 `expiresAt` 字段（课时有效期），但前端 `LoginResponse` 中 User 类型没有定义该字段。

**后端现状**:
```typescript
// backend/src/services/auth.service.ts
return {
  token,
  refreshToken,
  user: {
    id: user.id,
    phone: user.phone,
    name: user.name ?? undefined,
    nickname: user.nickname,
    avatar: user.avatar ?? undefined,
    role: user.role,
    grade: user.grade ?? undefined,
    age: user.age ?? undefined,
    school: user.school ?? undefined,
    expiresAt: undefined,  // login 方法中未设置
    isValidMember: undefined,
    permissions: undefined
  }
};
// passwordLogin 方法中设置了 expiresAt
return {
  user: {
    // ...
    expiresAt: user.expiresAt ?? undefined,  // 密码登录返回了
    // ...
  }
};
```

**前端现状**:
```typescript
// src/types/index.ts
export interface User {
  id: string;
  phone: string;
  name?: string;
  nickname?: string;
  avatar?: string;
  role: UserRole;
  expiresAt?: string; // ISO Date String - 已定义
  isValidMember?: boolean;
  permissions?: string[];
  grade?: string;
  age?: number;
  school?: string;
  classHours?: UserClassHours;
}
// LoginResponse 使用的是 User 类型，应该有 expiresAt
```

**问题分析**:
前端 `User` 类型已定义 `expiresAt` 字段，但后端 `login` 方法（验证码登录）返回的 user 对象中 `expiresAt` 被设置为 `undefined`。这意味着：
1. 验证码登录不会返回课时有效期
2. 只有密码登录会返回课时有效期

**修复建议**:
```typescript
// 后端 login 方法补充 expiresAt
return {
  user: {
    // ...
    expiresAt: user.expiresAt ?? undefined,  // 添加
    // ...
  }
};
```

### 问题 88：后端返回的 expiresAt 是 DateTime，前端期望 ISO 字符串

**优先级**: 低

**问题描述**:

**后端现状**:
```typescript
// backend/src/services/auth.service.ts
expiresAt: user.expiresAt ?? undefined,  // DateTime | null
```

**前端现状**:
```typescript
// src/types/index.ts
expiresAt?: string; // ISO Date String
```

**修复建议**:
```typescript
// 后端统一转换为 ISO 字符串
expiresAt: user.expiresAt?.toISOString() ?? undefined,
```

### 问题 89：RegisterPayload.password 在后端是可选的

### 长期优化（低优先级）

2. **添加权限缓存机制**: 优化 permissions 字段的获取性能

## 总结

auth（认证）模块整体功能完整，但存在以下类型不一致问题：

3. `RegisterPayload.password` 在后端类型定义中为可选

建议按优先级逐步修复类型定义和返回结构，确保前后端数据结构一致。
