# 文档命名规范

> 版本: v1.0  
> 更新日期: 2026-02-07

---

## 一、命名格式

**格式：** `功能-类型.md`

- 功能：描述文档所属的功能模块或业务领域
- 类型：标识文档的用途或性质
- 连接符：使用中划线 `-`

---

## 二、类型后缀对照表

| 类型后缀              | 含义     | 适用场景                       |
| --------------------- | -------- | ------------------------------ |
| `-api.md`             | 接口文档 | RESTful API 说明、接口参数     |
| `-test-case.md`       | 测试用例 | 自动化测试、手动测试用例       |
| `-guide.md`           | 操作指南 | 运维、部署、操作步骤、排查流程 |
| `-acceptance.md`      | 验收标准 | 上线验收清单、按角色验收要点   |
| `-architecture.md`    | 架构设计 | 系统设计、技术选型、数据流图   |
| `-deployment.md`      | 部署指南 | 环境搭建、CI/CD、发布流程      |
| `-troubleshooting.md` | 故障排查 | 问题排查、日志分析、常见错误   |
| `-spec.md`            | 需求规格 | 功能需求、业务规则、用户故事   |
| `-changelog.md`       | 更新日志 | 版本变更记录、功能迭代         |
| `-readme.md`          | 说明文档 | 项目说明、快速开始、索引入口   |

## 四、命名注意事项

### ✅ 正确示例

```
用户认证-api.md
问题创建-test-case.md
白名单管理-guide.md
部署流程-deployment.md
验收操作-acceptance.md
数据库操作-guide.md
```

### ❌ 错误示例

```
API接口文档.md         # 类型不明确
后端测试用例V2.md      # 功能不明确
需求文档               # 缺少类型后缀
新建文件夹/需求.md      # 路径中含空格
```

## 五、文档目录结构建议

```
docs/                          # 统一文档入口
├── README.md                  # 项目文档索引
├── guides/                   # 操作指南
│   ├── 快速开始-guide.md
│   ├── 环境配置-guide.md
│   ├── 数据库操作-guide.md
│   └── 部署流程-deployment.md
├── specs/                    # 需求与接口文档
│   ├── api/                  # API 文档
│   │   ├── 用户认证-api.md
│   │   └── 问题管理-api.md
│   ├── acceptance/          # 验收标准
│   │   ├── 学生端-acceptance.md
│   │   ├── 教师端-acceptance.md
│   │   └── 管理员端-acceptance.md
│   └── 功能-spec/            # 功能需求
├── architecture/             # 架构设计
│   ├── 系统架构-architecture.md
│   └── 数据模型-architecture.md
└── runbooks/                 # 运维手册
    ├── 故障排查-troubleshooting.md
    └── 监控告警-guide.md
```

## 六、命名一致性检查清单

- [ ] 所有文档使用中划线 `-` 连接
- [ ] 文档名使用中文（功能部分）和英文（类型后缀）
- [ ] 避免在文档名中使用空格
- [ ] 避免使用特殊字符
- [ ] 文档名长度适中（不超过 50 字）
- [ ] 同类文档使用统一的后缀

> **提示**：文档命名规范的目的是提高文档可发现性、降低协作成本。建议团队在创建新文档时始终遵循此规范。
