# 前端诊断工具与系统日志的接口联动判断方法论

> 目标：指导团队成员在使用前端诊断工具（`DiagnosticPage` + `runDiagnosticTests`）时，如何系统性地结合浏览器 Network、前端日志与后端系统日志，判断接口与整体链路的健康状况。

---

## 一、判断逻辑的具体步骤

### 1. 明确诊断目标与范围

1. 确定本次诊断的目标：
   - 快速验证「当前环境」的核心接口是否可用；
   - 回归某个功能改动（如登录流程、问题列表、行为埋点等）；
   - 排查用户反馈的问题是否可复现。
2. 明确 Diagnostic 工具当前能力：
   - `src/pages/DiagnosticPage.tsx`：负责展示测试列表、进度条、运行日志与统计信息；
   - `src/lib/test-runner.ts`：目前主要基于 mock 数据模拟典型接口行为（后续可替换为真实 API 调用）。

### 2. 启动诊断工具并触发测试

1. 启动前端开发环境（根目录）：
   - `npm install`（首次）；
   - `npm run dev`；
2. 在浏览器打开 Diagnostic 页面（实际路由以实现为准，如 `/diagnostic`）；
3. 点击「开始诊断」：
   - 观察顶部统计卡片（总用例数、通过/失败数、平均耗时）；
   - 观察中部测试列表中每个用例的状态（pending → running → success/failure）；
   - 观察右侧/底部的「运行日志」区域，记录每条日志对应的测试用例 ID 与结果。

### 3. 联动浏览器 Network 与后端日志

> 当前 `runDiagnosticTests` 使用 mock 数据，后续如接入真实接口时，建议按以下方法联动判断。

1. 打开浏览器开发者工具：
   - 切换到「Network」面板；
   - 勾选「Preserve log」或类似选项，确保不会丢失请求记录。
2. 再次运行诊断：
   - 对照 Diagnostic UI 中的每个测试用例（名称/说明），在 Network 中找到对应的 HTTP 请求（method + url）；
   - 确认请求发起时间与测试用例状态变化时间一致或在合理范围内。
3. 同时观察后端系统日志：
   - 在 `backend/` 目录运行 `npm run dev`（或测试命令）；
   - 观察 Pino 输出的访问日志（包含 `req.method`、`req.url`、`res.statusCode`、`responseTime`）；
   - 对于失败用例，检查是否有对应的错误日志（`type/status/code/error/path/method`）。

### 4. 建立「测试用例 → 请求 → 日志」的对应关系

对每个测试用例，尝试建立以下三向映射：

1. 测试用例信息：
   - `id`、`name`、`description`（来自 `test-runner.ts`）；
   - UI 里显示的状态（success/failure）与耗时。
2. HTTP 请求信息（如有真实请求）：
   - Network 中的 method、url、status、response body；
3. 后端日志信息（通过 requestId 或 method+url+时间戳关联）：
   - 访问日志：`res.statusCode`；
   - 错误日志：`type/status/code/error/path/method`。

### 5. 基于规范进行综合判断

1. 用例标记为 success 时：
   - Network 中的请求应返回 2xx（通常为 200/201），响应数据结构与测试期望一致；
   - 后端访问日志中对应请求的 `res.statusCode` 为 2xx；
   - 不应存在与该请求相关的 error 日志（`type='app_error'/'validation_error'/'unknown_error'`）。
2. 用例标记为 failure 时：
   - 检查是「预期失败」（测试故意模拟错误）还是「非预期失败」（真正问题）；
   - 对照用例说明查看期望状态码/错误码；
   - 检查后端错误日志是否记录了对应错误码与路径。

## 二、适用场景说明

### 1. 日常开发自检

- 新增或改动某个后端接口后，在前端接入前先用 Diagnostic 工具扩展对应用例（或替换为真实接口调用），用于快速验证：
  - 认证链路是否可用；
  - 关键业务接口的返回结构是否符合预期；
  - 错误码与文案是否正确。

### 2. 发布前回归与环境验证

- 在将新版本部署到测试/预发环境后：
  - 前端指向该环境的后端地址；
  - 在 Diagnostic 页面运行一轮完整诊断；
  - 结合系统日志，评估当前环境是否达到「可回归测试」的最低标准。

### 3. 问题定位与复现

- 当测试/运营反馈问题时：
  - 使用 Diagnostic 工具尝试在相同环境下复现；
  - 利用用例日志 + Network + 后端日志三方信息进行交叉验证；
  - 判断问题是前端调用错误、后端实现问题，还是环境配置问题。

### 4. 教学与新人培训

- 通过 Diagnostic 工具的可视化界面与日志输出，向新成员展示：
  - 如何从「用户行为」映射到「接口调用」；
  - 如何从「接口调用」映射到「后端日志与数据库行为」；
  - 形成完整的排查思路。

## 三、质量评估标准

### 1. 用例覆盖度

1. 功能覆盖：
   - 诊断用例应覆盖核心业务流程（认证、问题列表、问题详情、提问、互动、通知等）；
   - 对于关键接口（如支付/课时变更等，若有），应有专门的诊断用例或扩展测试。
2. 状态覆盖：
   - 每类接口至少包含「成功场景」与「失败场景」两类用例；
   - 失败场景应覆盖权限错误、参数错误、业务规则错误等。

### 2. 结果可信度

1. 一致性：
   - Diagnostic UI 显示的成功/失败结果，应与 Network 与后端日志的状态码和错误码一致；
   - 不允许出现「前端标记成功但实际接口失败」或相反情况。
2. 稳定性：
   - 同一环境下重复运行诊断，结果应高度一致（排除随机网络抖动影响）；
   - 对于故意设置的不稳定场景，用例描述中要明确说明。

### 3. 性能与体验

1. 单轮诊断耗时：
   - 总体耗时应在合理范围内（例如 < 30 秒，视用例数量而定）；
   - 超时接口应单独标记并在日志中体现。
2. UI 体验：
   - 进度条与状态更新及时，失败用例有清晰的文案与日志指引；
   - 日志区域支持滚动查看，便于分析。

### 4. 可维护性

1. 用例定义风格统一：
   - `id` 唯一且有语义（如 `auth_login_success`）；
   - `name` 与 `description` 清晰描述场景；
2. 代码结构：
   - `runDiagnosticTests` 中对测试用例的组织遵循结构化编程原则（顺序/选择，无复杂嵌套）。

## 四、常见问题的判断依据

### 问题 1：诊断工具显示失败，但接口看起来正常

**判断依据：**
1. 检查测试用例逻辑：
   - 是否使用 mock 数据，而非真实接口返回；
   - 断言条件是否与真实接口约定一致（字段名、类型、值范围）。
2. 检查 Network：
   - 是否实际发送了请求；
   - 返回数据是否满足用例中的断言。

**处理建议：**
1. 明确用例是「纯前端模拟」还是「真实接口验证」；
2. 如需真实验证，应重构用例，使其调用封装好的 API 客户端，并基于真实响应断言。

### 问题 2：诊断工具显示成功，但后台日志有大量错误

**判断依据：**
1. 检查是否存在其他并发请求（如页面自动轮询）造成错误日志；
2. 检查 Diagnostic 工具是否忽略了部分异常（例如 catch 了错误但未上报 failure）。

**处理建议：**
1. 在用例中对异常显式断言（例如预期某请求必须成功，否则标记为 failure）；
2. 对所有 catch 块增加日志输出，避免“吞异常”。

### 问题 3：诊断日志太多，难以定位关键失败

**判断依据：**
1. 日志中是否混入了大量无关调试信息；
2. 失败用例的日志是否有明确前缀或标签。

**处理建议：**
1. 为每条日志添加 `testId` 前缀，例如 `"[auth_login_success] ✅ PASS ..."`；
2. 对失败日志统一使用易于搜索的前缀（如 `❌ FAIL:`），并在文档中说明。

### 问题 4：测试结果在不同环境不一致

**判断依据：**
1. 检查环境配置（后端 Base URL、环境变量、Feature Flag 等）；
2. 检查后端部署版本及数据库数据是否同步；
3. 检查是否存在与环境相关的依赖（第三方服务、缓存等）。

**处理建议：**
1. 在 Diagnostic 页面中显示当前环境信息（如 API Base URL、版本号等）；
2. 在用例日志中记录关键环境信息，便于复现；
3. 在发布流程中将运行 Diagnostic 工具作为标准步骤，并记录结果。

## 五、最佳实践案例

### 案例 1：本地环境快速健康检查

**场景：** 开发者拉取最新代码，启动本地 Postgres/Redis 与后端服务后，希望快速确认环境是否正常。

**操作步骤：**
1. 启动后端：在 `backend/` 执行 `npm run dev`；
2. 启动前端：在根目录执行 `npm run dev`；
3. 打开 Diagnostic 页面，点击「开始诊断」；
4. 观察：
   - 所有核心用例（auth、question、behavior 等模拟用例）状态是否为 success；
   - 后端日志中是否有 5xx 或明显错误；
   - 平均耗时是否在合理范围内。

**结论：**
- 如全部通过且日志健康，可认为本地环境可用于功能开发与调试；
- 如某类用例持续失败，应先修复再进行大规模开发。

### 案例 2：回归登录链路改动

**场景：** 后端调整了登录与白名单逻辑，前端对登录表单也做了调整，需要验证链路是否闭环。

**操作步骤：**
1. 在 `test-runner.ts` 中新增或调整与登录相关的测试用例，使其调用真实 `/api/auth/send-code` 与 `/api/auth/login`；
2. 在 Diagnostic 页面运行测试；
3. 对于登录测试用例：
   - 检查 UI 是否标记为 success；
   - 在 Network 中确认请求返回 200/201，响应体结构正确；
   - 在后端日志中确认对应请求的 `res.statusCode` 为 2xx，且无错误日志。

**结论：**
- 若任一环节不符合预期，应按“请求→响应→日志”的路径逆向排查出问题点（参数格式、白名单数据、验证码逻辑等）。

### 案例 3：发现并验证性能回退

**场景：** 某次改动后，用户感觉列表加载变慢，需要客观判断是否存在性能回退。

**操作步骤：**
1. 在 Diagnostic 工具中为「问题列表加载」编写测试，用于记录加载耗时（如 mock 变为真实 API 调用后，记录从请求发起到渲染完成的时间）；
2. 在多个时间点运行诊断，并记录平均耗时；
3. 同时观察后端访问日志中的 `responseTime` 字段。

**结论：**
- 若前端测得的耗时与后端 `responseTime` 都明显增加，可以初步判断存在性能回退；
- 后续可结合数据库慢查询日志 / Profiling 等进行更深入分析。

## 六、执行建议

1. 将 Diagnostic 工具视为「前端 + 后端 + 环境」的集成健康检查仪表盘，而不是单纯的前端 demo 页；
2. 在新增重要功能或改动关键接口时，同步考虑是否需要为其补充或调整诊断用例；
3. 结合 `develop/判断方法论-系统日志与错误码.md`（后端侧方法论）一起使用，实现从前端操作，到接口返回，再到系统日志的完整判断闭环。
