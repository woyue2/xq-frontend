# 变更提案: 本地联调结构化日志与错误码记录

## 需求背景
在本地联合启动后端服务与前端应用进行接口联调或诊断测试时，需要能够从“系统日志”中直接看到每一次关键行动（如登录、提问、审核等）对应的成功码或错误码，以便快速定位问题、复现 bug 和编写测试报告。

当前后端已接入 `pino-http` 作为访问日志中间件，并通过统一错误处理中间件 `errorMiddleware` 返回结构化错误响应，但尚未形成一套清晰的“结构化日志 + 统一错误码记录”方案，也缺少针对本地联调场景的系统化文档和测试说明。

本提案旨在在不新增对外 API 的前提下，通过增强现有日志与错误处理机制，实现：
1. 每个请求在系统日志中都能看到 HTTP 状态码（正确码/错误码）；
2. 发生业务错误或验证错误时，日志中包含统一结构的 `code`/`error` 字段；
3. 方案遵循结构化编程与模块化设计，可测试性良好，并配套完善文档与测试。

## 变更内容
1. 后端日志中间件增强  
   - 在 `loggerMiddleware` 中统一配置 `pino-http`，确保每个请求日志包含 method、url、statusCode 等核心字段，并为后续诊断预留请求 ID（traceId）字段。  
2. 统一错误处理与错误日志记录  
   - 在 `errorMiddleware` 中统一对 `AppError`、`ZodError` 及未知错误进行结构化封装，补充使用 `req.log.error(...)` 记录包含 `status`、`code`、`error`、`path`、`method` 的错误日志，同时避免泄露敏感信息。  
3. 结构化编程与可测试性提升  
   - 按模块化与结构化编程原则整理日志与错误处理中间件：为核心函数补充前置条件/后置条件/异常说明，避免复杂嵌套与非结构化跳转。  
   - 为日志与错误处理相关逻辑编写单元测试，覆盖所有分支路径，新增代码块行覆盖率不低于 85%。  
4. 文档与部署说明同步  
   - 在后端编码规范与部署文档中补充“本地联调时如何查看系统日志中的正确码/错误码”的说明，形成面向开发与测试同学的使用指南。

## 核心场景

### 需求: 本地前后端联调时记录正确码/错误码
**模块:** 后端日志与错误处理中间件
在本地同时运行前端与后端，通过浏览器执行登录、发送验证码、提问等操作，希望能在后端系统日志中按时间顺序查看每次请求对应的 HTTP 状态码以及错误时的错误码信息。

#### 场景: 登录成功时记录正确码
前置条件：
- 后端通过 `npm run dev` 启动，`loggerMiddleware` 与 `errorMiddleware` 已按新方案生效；
- 前端或 Postman 向 `POST /api/auth/login` 发送合法请求。

预期结果：
- 响应 JSON 中返回 `code: 200`，HTTP 状态码为 200；
- 后端系统日志中存在一条对应请求的 info 日志，至少包含 method、url、statusCode=200。  

#### 场景: 验证码错误时记录错误码
前置条件：
- 用户向 `POST /api/auth/login` 提交错误验证码；
- 服务端抛出业务错误或验证错误。

预期结果：
- 响应 JSON 中返回 `code: 400` 或相应错误码，`error` 字段指明错误类型（如 `INVALID_CODE` 或 `VALIDATION_ERROR`），HTTP 状态码为 400；
- 后端系统日志中存在一条 error 日志，结构化字段包含 `status=400`、`code`、`error`、`path=/api/auth/login`、`method=POST`，便于后续诊断。  

#### 场景: 未知错误时记录内部错误
前置条件：
- 某接口内部抛出未捕获异常。

预期结果：
- 响应 JSON 中返回 `code: 500`、`error=INTERNAL_SERVER_ERROR`（不暴露具体内部细节）；
- 后端系统日志中记录 error 等级日志，包含错误堆栈（在安全前提下）及请求上下文，方便开发者本地复现与排查。

## 风险评估
- **风险 1:** 日志量增加可能影响 IO 性能  
  - **缓解:** 保持日志级别在开发/测试环境为 `info`，生产环境按照部署文档建议调优；避免记录完整请求体或大对象，仅记录必要字段。  
- **风险 2:** 日志中可能泄露敏感信息（如手机号、Token）  
  - **缓解:** 在错误日志与访问日志中避免直接输出敏感字段；如有需要可在 `pino-http` 中配置自定义序列化与字段遮掩。  
- **风险 3:** 中间件改动影响现有行为  
  - **缓解:** 通过单元测试覆盖所有分支路径，并在关键接口上增加简单集成测试；保持对外响应结构不变，减少对前端的影响。
