# 技术设计: 本地联调结构化日志与错误码记录

## 技术方案

### 核心技术
- 语言与框架：Node.js 18+、Express.js、TypeScript
- 日志：`pino` + `pino-http`（结构化访问日志）
- 验证与错误：统一 `AppError`、`ZodError` 与兜底错误处理
- 测试：Jest（已在 `backend` 中配置）、现有单元与集成测试框架

### 实现要点
- 复用并增强现有 `loggerMiddleware`：  
  - 继续使用 `pino-http` 作为访问日志中间件；  
  - 按需配置 `genReqId` 生成请求 ID，统一写入日志字段（用于诊断时串联多条日志）；  
  - 利用 `pino-http` 默认行为记录 method、url、statusCode 等字段，将 HTTP 状态码作为“正确码/错误码”的系统日志来源。  
- 统一错误处理与错误日志记录：  
  - 在 `errorMiddleware` 中根据错误类型区分处理：  
    - `AppError`：使用业务状态码与业务错误码；  
    - `ZodError`：返回统一 `VALIDATION_ERROR` 与 400 状态；  
    - 其他未知错误：返回 500 与通用错误码。  
  - 在构造响应 JSON 之前，通过 `req.log.error({...})` 记录结构化错误日志对象，至少包含：  
    - `type: 'http_error'`；  
    - `status`（HTTP 状态码）；  
    - `code`、`error`（业务错误码与枚举值）；  
    - `path`、`method`；  
    - 在非生产环境可选地附带 `stack` 信息。  
- 结构化编程与模块化设计：  
  - 日志与错误处理逻辑拆分为若干纯函数（例如内部辅助函数负责从错误实例计算响应结构、从请求构造日志上下文等），每个函数具备清晰的输入输出：  
    - 输入：错误对象、请求上下文、默认配置；  
    - 输出：可直接用于响应与日志记录的结构化数据。  
  - 避免在中间件中编写深层嵌套或隐式分支，所有分支逻辑均通过显式的条件判断与早返回实现。  
  - 为每个导出函数编写文档注释，说明前置条件（入参要求）、后置条件（返回值不变式）及可能抛出的异常，便于单元测试与后续维护。  
- 测试策略：  
  - 针对日志与错误处理中间件新增单元测试：使用伪造的 `req`、`res`、`next` 对象和注入的 `log` 替身（spy），验证不同错误类型下的响应与日志内容；  
  - 将新增代码的语句/分支覆盖率控制在 85% 以上，必要时通过 Jest 覆盖率报告核实。  

## 架构设计

- 逻辑位置：  
  - 访问日志与错误处理均处于 Express 中间件链路中，应用架构总体不变。  
  - 调用顺序：`helmet` → `cors` → `express.json` → `loggerMiddleware` → 路由层 → `errorMiddleware`。  
- 模块边界：  
  - `loggerMiddleware`：负责所有请求的访问日志（包括成功与失败），不理解业务语义，仅记录 HTTP 层面的信息。  
  - `errorMiddleware`：负责将异常转化为统一的 HTTP 与业务响应，并负责错误级日志记录；内部不直接操作数据库或外部服务。  
  - 业务服务与路由：保持现有职责，仅需确保业务错误通过抛出 `AppError` 交由统一错误处理中间件处理。  

（本变更不引入新的高层架构组件，因此省略 Mermaid 架构图。）  

## 架构决策 ADR

### ADR-001: 使用 HTTP 状态码作为日志中的“正确码/错误码”主来源
**上下文:**  
系统已有统一响应结构，其中 `code` 字段与 HTTP 状态码保持一致，大部分错误场景还会附带 `error` 字段标识错误类型。需求提出“在本地联调时把对应行动返回的错误码或正确码写入系统日志”，本质上是希望在日志中建立“动作 → 状态码/错误码”的清晰映射。  

**决策:**  
- 访问日志中以 HTTP 状态码（`res.statusCode`）作为“正确码/错误码”的主来源；  
- 在错误日志中追加 `code` 与 `error` 字段，用于细化分类与排查；  
- 不新增额外的错误码体系，避免与现有响应结构产生不一致。  

**理由:**  
- 保持现有对外 API 契约不变，避免前端与测试用例大规模调整；  
- 复用 `pino-http` 的高性能结构化日志能力，减少自研日志系统的复杂度；  
- 在日志查询与告警系统中，HTTP 状态码是最通用、可移植的监控维度。  

**替代方案:**  
- 替代方案A：新增“诊断日志上报 API”，由前端主动上报业务码与场景信息 → 拒绝原因：增加前端改造与后端 API 维护成本，与当前需求“本地联调 + 系统日志”不完全匹配。  
- 替代方案B：在所有路由中显式记录业务日志（包含 code） → 拒绝原因：侵入性较高，容易造成重复代码与维护成本。  

**影响:**  
- 短期内仅增强中间件，不改动业务层；  
- 日志分析与监控可直接使用 HTTP 状态码与错误码字段进行筛选与聚合；  
- 如未来需要引入更细粒度的业务码体系，可在现有结构上平滑扩展。  

## API设计

- 本次变更不新增对外 API，也不改变现有接口路径与请求参数。  
- 响应结构保持与 `codex-develop-doc/后端-测试用例.md` 中定义的一致：  
  - 成功响应：`{ code: 200, message: string, data: T, timestamp }`  
  - 错误响应：`{ code: number, message: string, error: string, timestamp, ... }`  
- 在错误处理中间件内部针对不同错误类型决定 `code` 与 `error` 的值，同时记录对应错误日志。  

## 数据模型

- 不增加新的数据库表或字段。  
- 如后续需要对错误日志做长期分析，可考虑在后续迭代中引入专门的持久化错误日志表或外部日志系统，目前阶段仅依赖 stdout / 日志采集系统。  

## 安全与性能

- **安全:**  
  - 避免在日志中直接输出敏感信息（如手机号、验证码、Token 等）；  
  - 在错误日志中，如需记录堆栈信息，建议仅在开发/测试环境开放，生产环境可通过环境变量控制日志内容；  
  - 对外响应中继续隐藏内部异常细节，仅返回通用错误文案。  
- **性能:**  
  - 避免在日志对象中放入大体积数据（如完整请求体或大型响应）；  
  - 继续沿用 `pino` 的高性能 JSON 日志格式，交由宿主机或容器的日志系统统一轮转与采集。  

## 测试与部署

- **测试策略:**  
  - 单元测试：  
    - 针对 `errorMiddleware` 的三类路径（`AppError`、`ZodError`、未知错误）分别构造伪造请求与响应对象，断言响应结构与 `req.log.error` 调用参数均符合预期；  
    - 针对 `loggerMiddleware`，构造简单请求与响应生命周期，验证日志函数被调用且包含 statusCode 字段。  
  - 覆盖率目标：  
    - 新增或变更的中间件与辅助函数，语句/分支覆盖率不低于 85%；  
    - 通过 `npm test -- --coverage` 或 Jest 配置生成覆盖率报告，作为测试报告的一部分。  
  - 手工验证：  
    - 本地同时运行后端与前端，执行典型业务路径（登录成功、验证码错误、未知错误模拟），通过控制台或日志文件确认日志中包含预期字段。  

- **部署与使用指南（与部署文档对齐）:**  
  - 本地开发：通过 `npm run dev` 启动后端，日志默认输出到标准输出（可重定向到文件，如 `backend/server.log`）；  
  - 测试/预发/生产：遵循 `deploy/1-总结.md` 与 `deploy/2-one-core-1g-deploy-notes.md` 中的建议，将日志交由宿主机或容器日志系统管理；  
  - 在 `helloagents/wiki/backend-deployment.md` 中补充“如何在本地联调与诊断时查看正确码/错误码”的具体步骤与示例。
