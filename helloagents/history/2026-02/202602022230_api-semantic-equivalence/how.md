# 技术设计: API 语义等价类分类与文档对齐

## 技术方案

### 核心技术与基础约定
- 不引入新的运行时依赖或框架，仅通过：
  - HelloAGENTS 知识库文档（`helloagents/wiki/*.md`、`helloagents/plan/*.md`）；
  - 需求/测试/前端 API 文档（`codex-develop-doc/*`、`gemini-frontend-doc/*`）；
  - 现有后端实现与 Jest 集成测试
  来建立统一的“语义等价类”分类与说明。
- 路由层面的「硬错误」仍由既有方案包 `202602022130_route-hard-errors` 负责，本方案只处理“实现与文档不完全同名但效果一致”的差异。

### 语义等价类分类规则

1. **类别 A：命名/文案差异，但语义一致**
   - 定义：HTTP 状态码、错误码（或等价业务码）、数据结构语义一致，仅字段名或提示文案不同。
   - 示例：
     - `/api/behavior/log`：
       - 文档示例：`message: "success", data: { logId }`；
       - 实际实现：`message: "Logged successfully", data: { id, success, receivedAt }`；
       - 语义：只要前端按“是否成功 + 日志标识”消费，该差异可视为语义等价。
   - 处理策略：
     - 在 `helloagents/wiki/api.md` 中，将文档字段与实现字段建立显式映射（例如说明 `logId` 即为实现中的 `id`），同时保留实现提供的附加字段说明；
     - 在路由 diff 或审查报告中，不将此类差异视为失败，而是标记为“语义等价类-A（命名差异）”并提示是否需要补文档。

2. **类别 B：返回体扩展字段（向后兼容增强）**
   - 定义：响应体在文档基础上增加了字段，但未删除或改变原有字段的含义，不会破坏依赖原合同的调用方。
   - 示例：
     - `POST /api/auth/send-code` / `login` / `register` 返回中增加了 `expireIn`、`cooldown`、更完整的用户信息或 `refreshToken` 等字段。
   - 处理策略：
     - 将文档中的“最小必需字段”与实现中的“实际字段 superset”区分开来，在 `helloagents/wiki/api.md` 中标注哪些字段是合同必需，哪些是扩展字段；
     - 在相关需求/测试文档中补充扩展字段说明，但不强制所有消费方立即使用；
     - 在差异检查中，将此类差异标为“语义等价类-B（扩展字段）”，默认不阻断。

3. **类别 C：扩展接口/参数（新增合同能力）**
   - 定义：实现新增了接口或参数，但保持对已有合同的完全兼容（旧接口仍然可用、语义未被破坏）。
   - 示例：
     - 认证模块新增的：
       - `POST /api/auth/register`
       - `POST /api/auth/refresh-token`
       - `POST /api/auth/logout`
     - 用户互动模块新增的：
       - `GET /api/users/me/likes`
       - `GET /api/users/me/favorites`
     - 这些接口在实现与测试用例中已经稳定，部分文档/前端清单在早期版本中未完全体现。
   - 处理策略：
     - 在 `helloagents/wiki/api.md` 的模块级接口列表中，将上述接口列为正式合同，并标记为「扩展能力」；
     - 在 `helloagents/plan/backend-route-diff.md` 中，将这类条目标记为“语义等价类-C（扩展接口）”，并明确说明：它们不是缺失路由，而是文档需补充的能力；
     - 在前后端文档中同步补齐这些接口，避免“有功能但没人知道”。

4. **类别 D：硬错误（不属于语义等价类，本方案只做边界说明）**
   - 定义：满足任一条件即为硬错误：
     - 文档声明存在的接口在实现中完全不存在（实际 404）；
     - HTTP 状态码与合同不符且改变业务语义（例如应 201 却返回 200 且前端依赖语义不同）；
     - 缺失文档中明确约定的必填字段或字段语义发生破坏性变化；
     - 路径/HTTP 方法严重不匹配（如文档 `POST`，实现仅有 `GET`）。
   - 处理策略：
     - 由 `202602022130_route-hard-errors` 方案负责修复或统一前后端；
     - 在本方案的文档中仅作为“语义等价类的负例”进行说明，防止误分类。

### 文档与知识库更新设计

1. **`helloagents/wiki/api.md`**
   - 新增「语义等价类分类规则」章节，按照上述 A/B/C/D 四类阐述：
     - 分类定义与判定原则；
     - 典型接口表格（接口路径、模块、类别、说明）；
     - 与 `route-hard-errors` 方案的关系（互斥且互补）。
   - 在认证、互动、埋点相关子章节中，为以下接口补充或修正描述：
     - `/api/auth/register`、`/api/auth/refresh-token`、`/api/auth/logout`；
     - `/api/users/me/likes`、`/api/users/me/favorites`；
     - `/api/behavior/log`。

2. **`helloagents/plan/backend-route-diff.md`**
   - 在现有差异清单基础上：
     - 增加“类型/分类”列，用于记录每条差异是「硬错误」还是 A/B/C 类语义等价；
     - 将用户已列举的接口标记为 C 类扩展接口或 A/B 类语义等价；
     - 明确指向 `202602022130_route-hard-errors` 方案，避免重复定义硬错误列表。

3. **`codex-develop-doc/后端需求文档-完整版.md`**
   - 在认证与行为埋点章节中：
     - 核对 `/api/auth/register`、`/api/auth/refresh-token`、`/api/auth/logout`、`/api/behavior/log` 的请求/响应示例，使其与实现和测试用例一致；
     - 对“示例简化 vs 实际返回 superset”的情况，用文本说明其为“扩展字段/语义等价”的典型场景。

4. **`codex-develop-doc/后端-测试用例.md`**
   - 复核与上述接口相关的用例：
     - 确认预期响应与现有实现一致（测试目前已以实现为准）；
     - 在用例描述中显式注明哪些检查点属于“合同刚性要求”，哪些属于“扩展字段验证”，并与 A/B/C 分类对应。

5. **`gemini-frontend-doc/前端API对接检查清单.md`**
   - 在认证、互动、埋点等检查项中：
     - 补充注册、刷新 token、退出、我的点赞/收藏等接口说明；
     - 对于语义等价类，强调前端只依赖语义稳定的字段，避免对辅助文案或冗余字段产生强依赖。

## 架构设计

本方案不引入新的架构组件，仍沿用现有：
- 后端：Express + TypeScript + Prisma；
- 文档：以 `helloagents/` 知识库为 SSOT，`codex-develop-doc/` 与 `gemini-frontend-doc/` 作为面向业务/前端的展开；
- 方案包：使用本方案包与 `route-hard-errors` 方案包配合管理“合同一致性”的不同维度。

## 安全与性能
- 本次变更不涉及运行时逻辑的修改，仅在极少数情况下可能引导未来对错误码/响应格式做微调，届时应遵循：
  - 先更新测试与文档，再谨慎调整实现；
  - 避免在未充分评审的情况下，将真正的安全相关错误（鉴权、限流等）归为语义等价类。
- 不涉及性能敏感代码路径。

## 测试与部署
- **测试策略:**
  - 在实施阶段完成文档更新后，运行现有后端 Jest 测试与 API smoke 测试脚本，确认语义等价类接口全部通过；
  - 如有前端 Playwright 或联调脚本，可选取注册 + 我的点赞列表 + 行为埋点等路径进行抽样验证。
- **部署:**
  - 仅知识库与文档变更，不需要额外部署步骤；
  - 若后续根据本方案推动少量实现层调整（例如统一 message 文案），需按照常规后端发布流程执行。
