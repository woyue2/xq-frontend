## 背景与问题描述

- 当前 Playwright 用例 `前端主流程冒烟测试 / 学生完整链路：提问 → 我的问题 → 点赞/收藏 → 问题详情` 在「我的提问」页面找不到刚刚创建的问题标题，导致用例在 `toBeVisible()` 超时。
- 手动排查过程中发现：后端 `/api/questions` 列表原本默认只返回 `status=approved` 的问题，而 E2E 场景中新创建的问题处于 `pending` 状态；同时，日志中部分接口曾出现 `TITLE_TOO_LONG` 等 4xx 业务错误，但缺乏针对问题流的系统化诊断。
- 用户要求：优先保证功能正常、链路可用，不做过度复杂改造；同时希望通过“日志 + 错误码”的方式更高效地发现和定位类似问题。

## 目标

1. 确保学生通过 `/create` 提交问题后，可以在「我的提问」列表中立即看到该问题，并能进入详情页再进行点赞/收藏操作，Playwright 主流程用例稳定通过。
2. 为“问题创建 + 我的提问列表 + 点赞/收藏”链路建立一套**基于结构化日志与错误码的诊断闭环**，在本地或 CI 中一键扫描非 2xx / 业务错误码，快速定位问题接口。
3. 在不破坏现有对外合同的前提下，对齐后端实现与文档中关于「我的提问」的约定（按 `authorId` 过滤时返回所有状态的问题）。

## 非目标

- 不重构整套问题模块/权限系统，只做围绕“我的提问 + 日志诊断”的最小必要改动。
- 不强制将所有历史接口改造成统一的新路由（例如新建 `/api/profile/my-questions`），在现有 `/api/questions` 基础上增量演进。
- 不引入新的外部日志基础设施（如 ELK、Prometheus 等），仅在现有 Pino 日志 + 本地文件扫描脚本基础上增强。

## 成功标准

1. E2E：`tests/e2e/main-flow.spec.ts` 中第三个用例在本地稳定通过，多次重复运行不会因数据残留或状态过滤问题导致间歇性失败。
2. 后端：新增或调整的 `/api/questions` 列表语义满足：
   - 未指定 `authorId` 时默认 `status=approved`，用于首页等公开列表；
   - 指定 `authorId` 时不过滤状态，由前端自行按 `pending/approved/...` 分组展示，满足「我的提问」场景。
3. 诊断：运行日志扫描脚本后，可以按路径看到 `/api/questions`、`/api/internal/test-token` 等接口的错误分布（HTTP 状态 + 业务错误码，如 `TITLE_TOO_LONG`、`MEMBER_EXPIRED` 等），用于快速确认是否存在隐藏异常。
4. 文档与知识库：在现有后端需求文档与 API 对接清单中，明确记录 `authorId` 查询语义与相关错误码示例，使“实现 ≈ 文档”保持语义等价而非偏差。
