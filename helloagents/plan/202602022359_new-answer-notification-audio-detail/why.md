# 方案2：新回答通知直达「语音回答详情」的联动设计（仅规划，暂不实施）

> 状态：仅规划，尚未执行（未来迭代用）
>
> 关联方案：`202602022350_answer-notification-on-answer-created`（老师回答完成后生成“有新回答”通知的基础方案）

## 一、背景与动机

- 现有/规划中的能力：
  - 当老师创建回答时，后端会为问题作者（学生）生成一条 `type='new_answer'` 的站内通知（见关联方案）。
  - 学生可以在通知中心看到该通知，并点击返回到 `/question/:id` 的问题详情页。
- 新的现实需求：
  - 老师回答中已经支持语音回答（单段录音 ≤ 60 秒、支持重录），学生更关心“直接听老师怎么说”；
  - 从“有新回答”通知进入问题详情后，如果回答列表较长，学生需要手动寻找最新回答，体验不够顺滑；
  - 希望实现：学生在通知中心点击“有新回答”→ 直接进入对应问题详情，并**自动定位到该条老师回答（包含语音播放器）**。

## 二、目标与非目标

### 2.1 目标

- 在不破坏现有通知与回答功能的前提下，补充精细联动：
  - 通知数据中携带**回答维度的定位信息**（例如 `answerId`）；
  - 前端在从通知跳转到问题详情后，能够：
    - 自动滚动到对应回答卡片；
    - 在 UI 上进行轻量高亮（例如浅色背景或边框高亮）；
    - 对带语音的回答确保播放器组件可见且可直接点击播放。

### 2.2 非目标（本方案不做）

- 不引入 WebPush / AppPush 等实时推送，仅优化站内通知→详情页的体验；
- 不改变现有“回答创建即发送通知”的时机与次数策略；
- 不在本轮微调语音播放器本身的交互（如倍速逻辑、可视化波形等）。

## 三、范围界定

### 3.1 后端范围

- 针对 `Notification` 的 `new_answer` 类型，在不修改数据库 schema 的前提下：
  - 通过 `content` 或约定格式携带 `answerId`；
  - 或在后续迭代中按需扩展字段（例如新增 JSON payload 字段，当前仅在方案中预留，不立即执行）。
- 在 `AnswerService.create` 中扩展已有通知创建逻辑：
  - 让通知能够同时携带 `questionId` + `answerId` 这两个维度的信息；
  - 保证事务完整性，不影响回答创建的主流程。

### 3.2 前端范围

- 通知中心页面 `NotificationsPage`：
  - 识别带有 `answerId` 的新回答通知；
  - 在点击通知时，把 `questionId` + `answerId` 一并编码到跳转中（URL 查询参数或导航状态）。
- 问题详情页 `QuestionDetailPage`：
  - 在加载回答列表后，根据 `answerId` 自动：
    - 找到对应回答卡片；
    - 滚动到该卡片位置；
    - 对该卡片做轻量高亮；
    - 如果回答包含语音播放器，保证其在首屏可见并可立即播放。

### 3.3 测试范围

- 后端集成测试：验证通知 payload 中 `answerId` 携带与解析逻辑；
- 前端 E2E：验证“学生从通知中心点击『有新回答』→ 自动定位到带语音的老师回答卡片”的完整链路。

## 四、价值评估

- 提升学生发现老师新回答（尤其是语音回答）的效率，减少“来回翻找”的时间；
- 为后续更复杂的联动（例如“新评论通知直达某条评论”）提供通用设计模式；
- 通过方案与任务拆解将实现逻辑与当前录音功能解耦，避免在本轮实现中增加不必要复杂度。+
