# 变更提案：题目「解题方法/办法」维度配置化（方案2）

> 状态：仅规划，尚未执行（未来迭代用）

## 一、背景与问题

- 当前「解题方法」维度完全由前端静态配置驱动：
  - 选项来源于前端 `TAXONOMY` 配置，修改选项或文案需要改代码并重新发布前端；
  - 所有提问入口的行为基本固定，无法按业务需要灵活启用/关闭该维度。
- 业务上存在以下需求与痛点：
  - 有些题目**确实不需要方法**，此时在创建问题页强行展示或要求选择“解题方法”会干扰老师提问流程；
  - 老师/运营希望可以在后台直接配置：
    - 该维度是否启用（启用时在提问页面展示，关闭时完全不显示）；
    - 维度显示名称（如「解题方法」「办法」「解题思路」等）；
    - 选项集合（如「配方法」「代入法」「图像法」「暂不确定」等），并能随时增删改；
  - 用户已经明确希望在方法选项中长期保留一个“暂不确定”选项，对应存储值为 `'unknown'`，并且显示在下拉框底部。
- 目前实现的主要问题：
  - 方法维度与题目模型的绑定是“弱耦合”的：仅通过 `tags` 数组中某个字符串表达，缺少显式的维度语义；
  - 所有选项写死在前端配置中，无法从后台管理或按环境/运营策略调优；
  - 无统一机制支撑将来其它题目维度（例如题型、难度标签等）的配置化需求。

## 二、目标与价值

- 在不破坏现有提问与回答主流程的前提下，先围绕**「解题方法/办法」维度**落地一套可配置机制，具备以下能力：
  - 后台可配置：
    - 维度是否启用；
    - 维度显示名称；
    - 可选项列表（含 `'unknown'` 对应的“暂不确定”选项）。
  - 前端所有**创建问题**相关页面通过接口获取该配置：
    - 当维度 `enabled = false` 时，不渲染该下拉框，对老师完全隐藏；
    - 当 `enabled = true` 时，使用后端返回的 label + options 渲染；
    - `'unknown'` 选项固定出现在下拉列表最底部。
  - 持久化仍兼容当前 `Question.tags` 存储方式，避免一次性重构题目模型。
- 从长期看，本方案为“题目维度配置 + 后台管理 + 前端动态下拉”提供一个通用骨架：
  - 设计足够通用的数据模型与接口，使后续增加其它维度（如“题目类型”“知识点标签”等）时可以复用；
  - 将维度的开关、文案与选项从代码中迁出到数据库/配置层，由后台界面维护。

## 三、范围界定

### 本轮方案2包含内容

- 仅围绕**一个维度**——「解题方法/办法」（key 暂定为 `method`）进行配置化设计与规划：
  - 设计通用的数据表结构与 API，但实施阶段只创建并使用 `method` 这一维度；
  - 前端的改造范围限定在「创建问题」相关页面（包含学生/老师端所有提问入口）。
- 后端：
  - 设计用于存储题目维度配置及选项的模型；
  - 设计读取配置的公开接口（供提问页面使用）；
  - 设计后台管理接口（供运营/老师在后台页面修改配置）。
- 前端：
  - 提问页面从接口读取方法维度配置并据此渲染下拉；
  - 预留后台管理界面路由与基础交互（表单 + 列表），具体实现细节待实施阶段按本方案拆解。

### 明确不在本方案内的事项

- 不在本轮重构 `Question` 模型整体结构，只通过兼容方式继续使用或轻度约定 `tags` 字段；
- 不立即推广到其它维度（例如题型、难度、知识点等），仅保证方案具备复用潜力；
- 不实现复杂的权限体系和审计流水，仅规划基础“管理员/运营可配置”的能力；
- 不处理已有历史数据的批量迁移问题，后续可根据实际需要单独设计迁移脚本。

## 四、成功标准

- 从产品视角：
  - 当运营在后台关闭“解题方法/办法”维度后，所有提问入口不再展示该字段，老师提问体验保持顺畅；
  - 当运营配置新的方法选项（包括重命名为「办法」）后，无需重新发布前端即可生效；
  - 老师在创建问题时，如果不需要方法，可以不选择该维度；若不确定，可选择“暂不确定（unknown）”。
- 从技术视角：
  - 新增的数据结构和接口对现有提问流程向后兼容，不破坏当前线上行为；
  - 设计出的模型和接口足够通用，将来可以在不大改架构的前提下扩展到其它题目维度；
  - 为未来实施阶段预留清晰的任务拆解（见 `task.md`），便于按阶段渐进落地。
