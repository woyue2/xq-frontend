## 1. 图床 / 图片上传链路收尾

### 1.1 目标

- 在**本地/测试环境**：无需真实图床，也能稳定完成“提问页图片上传预览”流程。  
- 在**生产环境**：可选择接入真实图床（对象存储）或暂时使用 Mock 地址，但行为要可预期、错误提示友好。

### 1.2 当前现状

- 前端：
  - `CreateQuestionPage` 使用 `questionService.uploadImage(file)` 上传图片。
  - `uploadImage` 实现：压缩图片 → 调用 `/api/upload/signature?type=image` → 非 Mock 模式时向 `uploadUrl` 执行 `fetch(FormData)`。
  - `VITE_USE_MOCK` 控制是否走前端 Mock 分支（返回构造出的 image URL）。
- 后端：
  - `GET /api/upload/signature`（`backend/src/routes/upload.routes.ts`）返回固定的 `uploadUrl = "https://oss.example.com/upload"` + `key/policy/signature`，用于模拟第三方对象存储签名。
  - 当前未真正接入第三方存储，`https://oss.example.com/upload` 在本地环境必然失败。

### 1.3 待办事项

1. **本地/测试环境策略（必做，优先级 P0）**  
   - [ ] `FE`：确认 `.env.test` 中 `VITE_USE_MOCK=true`，并在本地开发环境按需开启：  
     - 开发阶段为方便起见，可在 `.env` 中暂时设置 `VITE_USE_MOCK=true`，避免请求外部图床。  
   - [ ] `QA`：在 Mock 模式下验证：`/create` 提问页上传 ≤3 张图片时能够成功预览，并可正常提交问题（即使实际图片只保存在 mock URL）。

2. **生产图床接入方案（可选 P1，视上线阶段决定）**  
   - [ ] `BE`：在 `backend/.env` 中预留图床配置：  
     ```env
     OSS_UPLOAD_BASE_URL=https://your-image-host.com/upload
     OSS_UPLOAD_TOKEN=your-token-here
     ```
   - [ ] `BE`：在 `backend/src/config/env.ts` 中扩展 `envSchema`：  
     - `OSS_UPLOAD_BASE_URL: z.string().url().optional()`  
     - `OSS_UPLOAD_TOKEN: z.string().optional()`  
   - [ ] `BE`：修改 `upload.routes.ts`：  
     - 若提供了 `OSS_UPLOAD_BASE_URL`，则 `uploadUrl` 使用该值（按需要拼接 token 或 query）；  
     - 否则维持原有 `"https://oss.example.com/upload"` 以兼容旧行为/测试。  
   - [ ] `QA`：在一个测试环境中接上真实图床（或测试桶），验证能上传 ≤1MB 图片，并在前端正常展示。

3. **错误提示与日志（P1）**  
   - [ ] `FE`：在 `uploadImage` 的 `catch` 中区分网络错误 / 签名错误 / 存储错误，适当调整 toast 文案，提升可理解性。  
   - [ ] `BE`：在后端增加针对 `/upload/signature` 的日志（使用 pino logger），包含 userId、type、key，但避免记录真实 URL/敏感 token。

## 2. AI 审核接入与安全性

### 2.1 目标

- 保持现有“人工审核 + 简易 AI 回调”的实现稳定可用；  
- 为未来接入真实 AI 审核服务预留清晰的扩展点；  
- 确保内部回调接口 `/api/internal/ai-check` 不被外部滥用，具备基础鉴权。

### 2.2 当前现状

- 后端：
  - 已实现 `POST /api/internal/ai-check`，可根据 `targetType + targetId + result.safe/score` 更新 Question/Answer/Comment 状态。
  - 已添加 `AI_INTERNAL_TOKEN` + `X-Internal-Token` 头部鉴权逻辑（可选开启）。
  - `ai-callback.api.spec.ts` 集成测试覆盖了问题/回答/评论的基础回调场景与未授权访问场景。
  - `deploy/ai-audit-worker.ts` 提供了“从 DB 拉取 pending 内容 → 调用 AI 服务 → 回调 backend”的 worker 示例。

### 2.3 待办事项

1. **内部回调鉴权（P0，安全必做）**  
   - [ ] `OPS/BE`：在生产环境的后端配置中设置：  
     ```env
     AI_INTERNAL_TOKEN=请生成至少32字节的高强度随机串
     ```
   - [ ] `AI 服务`：调用 `/api/internal/ai-check` 时必须带上：  
     ```http
     X-Internal-Token: $AI_INTERNAL_TOKEN
     ```
   - [ ] `QA`：在预发布环境验证：未带该头部时回调返回 `403/INTERNAL_ACCESS_DENIED`；带正确头部时回调流程正常。

2. **AI 服务接入与回调数据约定（P1）**  
   - [ ] `BE`：在 `codex-develop-doc/后端需求文档-完整版.md` 或独立文档中补充“AI 结果 JSON 格式约定”（`safe/score/reason/labels/provider/raw` 等）。  
   - [ ] `AI`：按约定输出结果，确保 backend 能稳定解析。  
   - [ ] `QA`：设计一组“安全内容 / 疑似违规 / 明显违规”的样例，验证 `status` 与前端展示的一致性。

3. **AI Worker 部署（可选 P2）**  
   - [ ] `OPS`：根据 `deploy/2-one-core-1g-deploy-notes.md` 中的建议，使用 crontab 或轻量队列，部署 `ai-audit-worker.ts` 周期性运行（注意控制每次处理条数，避免 1c1g 机器抖动）。  
   - [ ] `BE/OPS`：在日志中记录 worker 拉取/回调数量和失败情况，便于随时关闭 AI 审核而不影响人工审核。

## 3. 审核流程与白名单/课时逻辑复盘

### 3.1 目标

- 确保「白名单 → 注册/登录 → 课时有效期 → 提问/回答/评论 → 审核 → 展示」这条链路在代码与测试中闭环一致；  
- 明确家长/学生/教师三类角色的权限边界与课时约束。

### 3.2 当前现状（概要）

- 白名单：
  - `/api/admin/whitelist` 系列接口 + `WhitelistService` 已实现 CRUD 与软删，集成测试覆盖大部分场景。
  - `AuthService.sendCode` 已在 `type=register` 时对白名单手机号做检查，未在白名单时返回 `403/NOT_IN_WHITELIST`。

- 课时：
  - `ClassHoursService` / `/api/admin/class-hours` 提供查询与批量调整能力。  
  - `requireActiveMembership` 中间件对学生写操作做课时检查，教师/家长免课时限制（家长写操作仍由业务路由禁止）。

- 审核：
  - 管理端 `admin-audit.routes.ts` 支持 pending 列表、审核通过/驳回/封禁/置顶。  
  - AI 回调与人工审核结果均会更新内容 `status`，已由集成测试覆盖。

### 3.3 白名单 & 课时链路待办（P0–P1）

1. **白名单与注册/登录一致性（P0）**
   - [ ] `BE`：再核对一次 `AuthService.register` 和 `AuthService.login` 是否在所有入口都尊重白名单 / isActive / isBanned 逻辑（包括旧手机号登录）。  
   - [ ] `QA`：根据《后端-测试用例.md》中 WL/AUTH/CLASS-HOURS 用例，使用 Postman/Newman 或后端 Jest 组合跑一条完整链路：  
     - 未在白名单 → register 被拒；  
     - 加入白名单 → register 成功；  
     - 删除白名单 + isActive 调整 → 用户登录受限。

2. **课时过期边界（P0）**
   - [ ] `QA`：重点验证：  
     - 学生课时过期时，写操作（提问/回答/评论）被 `MEMBER_EXPIRED` 拦截；  
     - 点赞/收藏仍可用（与产品约定一致）。  
   - [ ] `BE`：如有不一致（例如某些写接口没挂 `requireActiveMembership`），按测试结果修正。

3. **审核逻辑疑点复盘（P1）**
   - [ ] `BE`：对以下路径做一次代码走读与手动用例验证：  
     - 问题/回答/评论从 `pending → approved/rejected/banned` 的状态机是否有非法跳转；  
     - 驳回/封禁原因存储字段是否统一（目前有用 `aiResult` 承载原因的实现）；  
     - 审核操作是否正确记录到 `AuditLog`（如有）。  
   - [ ] `QA`：借助 `backend/playwright/todolist.md` 中的 AU/AI 用例，验证「审核后前端列表/详情展示」是否符合预期。

## 5. 性能、监控与告警

### 5.1 性能与容量（1c1g）

已在 `deploy/2-one-core-1g-deploy-notes.md` 中有详细建议，计划层面重点：

- [ ] `OPS`：按文档设置 Postgres 连接数/内存参数，Prisma `connection_limit` 等。  
- [ ] `OPS`：使用 `docker stats` 或宿主机监控观察峰值内存/CPU，评估是否需要拆出 DB 或升级规格。  
- [ ] `QA`：选取典型压力场景（登录高峰、问题列表刷新、教师审核）做简单压测（可用 `scripts/perf-smoke.sh` 或外部工具）。

### 5.2 监控与告警

- [ ] `OPS`：至少接入以下监控项：  
  - 应用层：`/health` 成功率、响应时间；  
  - 系统层：CPU/内存使用率、磁盘使用情况；  
  - 数据库：连接数、慢查询。  
- [ ] `OPS`：配置基础告警规则：  
  - 持续 5 分钟 `/health` 出现非 200 → 通知；  
  - 内存使用 > 90% 持续 10 分钟 → 通知；  
  - 数据库连接耗尽或频繁重启 → 通知。
